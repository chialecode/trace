# 技术设计：远程版、上传与导入导出

本页说明远程版（`trace-server`，部署在 Linux VPS 上）应当怎样工作，以及它和本地 TRACE 之间的订阅同步、Cookie 推送、上传和资源库导入导出（[DEC-062](../decisions.md#dec-062)，需求 [FR-REMOTE-001～008](../requirements.md#remote-scope)）。进程分层与凭证见[架构](architecture.md)，条目文件夹与 `item.json` 见[数据与缓存](data-and-cache.md)，检查更新与规则见[订阅](subscriptions.md)，录制见[直播](live.md)。与代码不一致时按[冲突规则](../dev-rules/workflow.md#conflicts)处理。

<a id="roles"></a>
## 1. 角色与数据流

```text
本地 TRACE（Windows 桌面）                         远程 trace-server（Linux，无界面）
  订阅、规则、设置 ──HTTPS + 令牌 + 证书指纹──>  只按同步来的订阅检查更新、按规则缓存新内容与录制
  Cookie（只由本地续期）──────────────────────>  凭证文件（本机密钥加密），从不续期
  设置 › 远程：查看状态 <─────────────────────── 状态（登录、检查、缓存、录制、上传、磁盘）
                                                  导出目录（与媒体库同样的条目文件夹）
                                                        │ 内置上传：调用 rclone，按条目上传，成功后删本机文件
                                                        │ 或用户自己的定时 rclone（兼容）
                                                        ▼
  媒体库 › 导入 <── 用户从网盘下载的文件夹 ──────── 网盘（如 Google Drive）
```

- 远程只做四件事：按同步来的订阅检查更新、按订阅的缓存规则缓存新内容、按规则录制直播、把完成的文件上传。没有媒体库界面、解析、“我的”、全部缓存、补更早内容、播放和 Web 页面。
- 本地和远程是同一版本（DEC-062 ②）：协议与文件格式只认当前版本，版本不同就拒绝并提示更新，不做旧格式兼容。
- 为以后的集群模式（多台机器订阅同一批账号、汇成一个资源库）预留：每个安装有节点 ID；条目按条目键合并；导入不关心条目来自哪台机器（第 6 节）。

<a id="server"></a>
## 2. 程序与部署

- **独立程序**：`cmd/trace-server`，只链接 `internal/service` 及下层包与 `internal/remote*`，不链接 MyGo、`internal/ui`、`internal/player`、`internal/shell`（`tools/check` 检查 `go list -deps ./cmd/trace-server`）。`CGO_ENABLED=0` 静态编译，发行 `linux/amd64` 与 `linux/arm64`；Debian 12、Ubuntu 22.04 及以上不需要额外运行库。上传需要机器上有 `rclone`（TRACE 不打包它）。
- **命令**：
  - `trace-server init --data <数据目录> --export <导出目录> [--listen :47380] [--public-address <地址[:端口]>] [--name <名字>]`：建目录（`0700`）、节点 ID、自签名证书、访问令牌与凭证密钥，打印一次**连接码**（地址、令牌、证书 SHA-256 指纹）和推荐的 rclone 过滤规则；令牌只存哈希，之后不能再查看。连接码里的地址取 `--public-address`，不填时取本机第一个非回环地址（VPS 在 NAT 后面时要填公网地址）。
  - `trace-server run --data <数据目录>`：前台运行（交给 systemd 管理）；`SIGTERM` 按托盘“退出”的同一路径收尾（任务暂停、录制收尾，限时 30 秒）。
  - `trace-server token --data <数据目录>`：换新令牌并打印新的连接码，旧令牌立即失效。
  - `trace-server upload-test --data <数据目录>`：用当前上传设置传一个小测试文件再删掉，检查 rclone 与网盘配置。
  - `trace-server version`、`trace-server rclone-filter`。
- **文件**：数据目录放 `server.json`（监听地址、导出目录、节点 ID 与名字、令牌哈希、上传设置）、`tls/`（证书与私钥 `0600`）、`credentials/`（凭证与密钥 `0600`）、`library.db`、`updates.db`、`subscriptions.json`、`settings.json`、`logs/`；数据目录独占锁同桌面版（INV-14）。导出目录就是远程的缓存保存位置，布局与本地媒体库相同（[数据 §1](data-and-cache.md#storage)）。
- **发行包**：`go run ./tools/package -server` 交叉编译两个架构，输出 `dist/trace-server/` 下每个架构一个 `trace-server-<版本>-linux-<架构>.tar.gz` 与 `SHA256SUMS`（只留最新一份）。包内一个顶层文件夹，含 `trace-server`、`trace-server.service`、`README.md`、`THIRD-PARTY-NOTICES.txt`、`VERSION.txt`；`trace-server.service` 与 `README.md` 的正本在 `cmd/trace-server/deploy/`。
- **systemd**：`trace-server.service` 示例用专用用户 `trace`，`Restart=on-failure`、`NoNewPrivileges`、`ProtectSystem=strict`，`ReadWritePaths` 只放 `/var/lib/trace`（数据目录与 rclone 配置）和导出目录，`RCLONE_CONFIG` 指向服务能写的 rclone 配置，`TimeoutStopSec=45` 留够 30 秒收尾。部署说明（`cmd/trace-server/deploy/README.md`）写目录、用户、防火墙、`init`、systemd、rclone 配置与自己的 client_id、外部定时 rclone 的排除规则、凭证保护的边界与换包升级。
- **日志**：`<数据目录>/logs/trace.log`，同时写标准错误（由 journald 收集）；规则同桌面版，另外不记录令牌、连接码、请求体与 rclone 的输出原文（只记退出码与脱敏后的首行错误）。

<a id="api"></a>
## 3. 远程接口与安全

- **传输**：HTTPS（TLS 1.3），证书是 `init` 生成的自签名 ECDSA P-256 证书。本地客户端不信任系统证书库，只认连接码里的证书指纹（叶证书 DER 的 SHA-256），不一致就拒绝，并提示“远程证书变了”。连接码经 SSH 终端从 VPS 拿到，所以第一次连接就能确认身份，不需要“首次信任”。
- **鉴权**：每个请求带 `Authorization: Bearer <令牌>`，令牌 32 字节随机数，服务端只存 SHA-256，并用常数时间比较。同一来源地址 1 分钟内失败 5 次后，10 分钟内一律 `429`。请求体上限 1 MiB（订阅快照与凭证），没有 CORS，不提供网页。
- **版本**：请求与响应都带 `X-Trace-Protocol`（当前 `1`）和程序版本；协议不同返回 `409`，本地显示两边的版本并提示更新较旧的一边。
- **端点**（`/api/v1/`，JSON）：

| 方法与路径 | 做什么 |
| --- | --- |
| `GET status` | 第 7 节的状态 |
| `GET subscriptions` | 远程当前的订阅快照与它的摘要哈希（本地据此显示“有改动未同步”） |
| `PUT subscriptions` | 用本地的订阅快照整体替换远程的（第 4 节） |
| `PUT credentials/{site}` | 推送一个站点的 Cookie（第 5 节） |
| `DELETE credentials/{site}` | 清除远程这个站点的登录 |
| `POST upload/retry` | 让失败的上传立即重试 |

- **本地保存**：连接的地址、名字与证书指纹放 `settings.json` 的 `remote`；令牌放凭证库（Windows DPAPI，与站点凭证同样保护），不进设置文件、日志与界面。

<a id="sync"></a>
## 4. 订阅同步与远程的规则

- **订阅快照**（与“导出订阅”文件同一格式，第 6.3 节）：订阅（ID、名字、关联账号的站点——含哔哩哔哩、抖音、微博、X——、UID、名字与头像地址、选用的规则 ID）、共用缓存规则，以及设置的一部分：画质、编码顺序、音质、多 P、并发、弹幕、字幕、AI 字幕、定时检查间隔、开播检查间隔。不同步代理、保存位置、窗口与播放器设置，也不含 Cookie。
- **整体替换**：远程的订阅、规则与上面这些设置换成快照里的。账号的检查起点（含置顶与微博快转基线）、上次检查与已发现的更新按“站点 + UID”保留，移出快照的账号不再检查，已缓存的文件不删（INV-11）。替换在一次写入里完成，失败就保持原样。
- **只缓存启动之后的新内容**：远程第一次检查一个账号时只建立起点（INV-12），起点之前的内容永远不缓存；远程停机期间发布、起点之后的内容在恢复后照常补上（受每轮页数限制）。远程不执行“全部缓存”（规则里的这一项对四个站点均在远程忽略，状态里注明），也没有补更早内容和手动缓存。
- **规则照常**：每个订阅按自己的规则决定是否定时检查、自动缓存哪些类型、是否开播录制（微博账号按[直播 §6](live.md#weibo)、X 账号按[直播 §7](live.md#x) 排除开播检查与录制，照常按规则检查更新与自动缓存）。远程的总开关“定时检查更新”始终打开（不然它什么也不做），所以选用“默认”规则的订阅在远程不会被检查。每小时额度、退避与熔断与桌面版相同（INV-10，哔哩哔哩 200 / 抖音 120 / 微博 100 / X 60），远程与本地各算各的。
- **本地与远程都缓存同一条**时，导入时这一条按“相同”跳过或按冲突处理（第 6.2 节）；不需要本地关掉自动缓存。

<a id="credentials"></a>
## 5. Cookie 推送与续期

- **只由本地续期**（DEC-062 ③）：哔哩哔哩续期会让旧 Cookie 失效，所以远程从不续期，也不调用任何登录接口。推送内容只有站点 Cookie 和账号摘要（UID、昵称），不推送 `refresh_token`。
- **推送时机**：用户在“设置 › 远程”点“同步 Cookie”；哔哩哔哩、抖音与微博在本地续期成功、重新扫码或粘贴登录后，只要配置了远程，就自动推送一次；推送失败（离线、证书不符、令牌错）时记为“Cookie 待同步”，之后每次刷新远程状态和每 10 分钟后台重试，成功后清除标记。**X 例外（DEC-066、FR-X-009）**：本地登录或重新登录 X **绝不自动推送**，推送失败也不进入后台待同步自动重试；只在用户在“设置 › 远程”点击 X 行的“同步 Cookie”、在弹出的确认框中阅读并明确确认 VPS 机房 IP 风险提示（“在云服务器的网络上用网页 Cookie 访问 X，被要求验证或锁号的可能明显高于家里的网络，不建议本地和远程同时用同一个 X 账号检查”，确认仅对这一次推送有效）后，才向远程手动推送一次。
- **远程验证**：`PUT credentials/{site}` 接受全部有效站点（`bilibili`、`douyin`、`weibo`、`x`）。收到后先用 nav（哔哩哔哩）、`profile/self`（抖音）、PC 两步严格校验（微博：`getBasicInfo` → `profile/info?screen_name=` 且昵称一致）或 X 两步严格校验（`settings.json` → `UserByScreenName` 且核对 `screen_name` 与 `twid`；缺 `auth_token` 或 `ct0` 本地 0 请求拒绝）校验一次，失败不保存，原凭证保持不变，并把原因返回本地（含 `schema_changed` 分类说明）。
- **失效**：远程请求得到“未登录”时，把这个站点标为“需要重新同步 Cookie”，停止这个站点的全部请求（INV-07），不影响其余站点，直到收到新 Cookie。
- **远程的凭证保存**：`credentials/` 下按站点存，用 `init` 生成的随机 32 字节密钥做 AES-GCM 加密，密钥文件 `0600`。这只能挡住把凭证文件单独拷走，挡不住拿到这台机器 root 权限的人；部署说明要写明这一点。不再使用非 Windows 下固定派生密钥的做法。

<a id="export"></a>
## 6. 导出目录、上传与导入

<a id="export-format"></a>
### 6.1 导出格式（远程导出目录、网盘上的副本、本地导出的文件夹都是这一种）

- **布局**：与媒体库相同，`<站点>/<作者>/<种类>/<条目>/`，里面是媒体文件和 `item.json`。`item.json` 就是这个条目的清单：`media` 列出每个文件的相对路径、字节数与 SHA-256（直播的每段同样）。
- **写入顺序**：先把媒体文件以正式名写完、校验通过，最后原子写 `item.json`。直播每收尾一段就重写一次 `item.json`，列出这一场到此为止的全部正式段（包括已经上传、本机已删掉的段）。
- **正在写的文件都有标记**：下载与录制中的文件以 `.part` 结尾，原子写入的临时文件以 `.trace-` 开头（`storage.WriteFileAtomic`、合并、图片与音频临时文件统一改成这两种）。DASH 视频的音视频分轨在合并成 `P01.mp4` 之前也用 `.trace-P01.video-….m4s` 这类名字；旧版本留下的 `P01.video-….m4s` 续传时先改成新名字再继续。所以任何上传方式只要排除 `*.part` 和 `.trace-*`，就不会传出写了一半的文件；`trace-server rclone-filter` 打印这两条规则。
- **可携带的清单**：导出、上传到网盘的 `item.json` 去掉只对本机有意义的字段（本机条目文件夹 `itemDir`、`itemKey`、`rawId`、`totalBytes`），其余与本地相同；导入时按条目内容重新算出这些字段。
- **节点**：`item.json` 新增可选字段 `cachedBy`（`node`、`name`）：缓存它的机器。旧条目没有这个字段；本地缓存的写本机节点 ID（`<数据目录>/node.json`）。
- **允许文件被搬走**：远程不依赖导出目录里的文件继续存在。是否已缓存、录到第几段只看远程自己的数据库与录制状态；文件夹被搬空后，下次写入时重新建立。远程不对导出目录做升级检查、丢失文件扫描和重建索引。

<a id="upload"></a>
### 6.2 内置上传（推荐，DEC-062 ⑨）

- **方式**：`server.json` 的 `upload`：`mode`（`rclone` 或 `none`）、`remote`（rclone 远端路径，如 `gdrive:trace`）、`rclone`（程序路径，默认在 `PATH` 里找）、`config`（可选的 rclone 配置文件路径）、`deleteAfterUpload`（默认开）、`extraArgs`（追加参数，如带宽限制）。网盘授权由用户用 `rclone config` 完成；TRACE 不读取也不保存 rclone 配置里的令牌。
- **单位与顺序**：一个条目的一批新完成文件为一次上传。先上传媒体文件（`rclone copy <条目文件夹> <远端>/<相对路径> --files-from <清单>`），成功后再上传 `item.json`。所以网盘上出现某个版本的 `item.json` 时，它列出的文件已经先传过。直播每收尾一段上传一次这一段与新的 `item.json`。
- **确认与删除**：rclone 退出码为 0 才算成功。成功后记入远程数据库（路径、字节数、SHA-256、时间）；`deleteAfterUpload` 开着时，只删除刚确认上传的正式文件，以及变空的文件夹（INV-09）。录制中的 `.part` 与还没写完的条目从不上传、不删除。
- **失败**：按退避重试（1、5、15、60 分钟，之后每小时）；rclone 找不到、配置错误、网盘配额（如 Google Drive 每天 750 GiB 的上传上限）分别在状态里说明。导出目录剩余空间低于 5 GiB 时状态显示警告，低于 1 GiB 时暂停新的缓存任务（录制按直播的磁盘规则）。
- **外部定时上传**（`mode: none`，兼容用户原来的做法）：TRACE 不上传也不删除；用户自己的定时 `rclone copy` 或 `rclone move` 加上 `--exclude "*.part" --exclude ".trace-*"`（建议再加 `--min-age 2m`）。用 `move` 时远程照常工作（第 6.1 节）。

<a id="import"></a>
### 6.3 资源库导入（本地，DEC-062 ④）

- **入口**：媒体库“⋯ → 导入…”打开媒体库里的导入页（标题“导入”，左上角返回媒体库），填一个文件夹路径（网盘下载下来的、另一台 TRACE 的缓存文件夹或导出文件夹，选它或它的上一层都可以；按 `<站点>/<作者>/<种类>/<条目>` 认出相对路径）。没有系统的文件夹选择框，路径直接输入或粘贴。先扫描、只读，列出预览，用户确认后才写入。
- **逐条判定**（条目键相同即同一条目，与来自哪台机器无关）：

| 分类 | 条件 | 默认处理 |
| --- | --- | --- |
| 新条目 | 本地没有这个条目键 | 导入 |
| 可补充 | 本地已有，导入的多出本地没有的文件（如新录的段、补全的分 P），同名文件内容一致 | 只补多出的文件，合并 `item.json` |
| 相同 | 文件集合与内容都一致 | 跳过 |
| 冲突 | 同一路径的文件字节数或 SHA-256 不同，或同一条目在不同的作者文件夹 | 等用户选：保留本地 / 用导入的 / 合并 |
| 未传完 | `item.json` 列出的文件缺失、字节数不符或 SHA-256 不符 | 能校验通过的文件照常导入（条目标为部分完成，没校验通过的文件记在 `missing`），其余等下次导入补上；一个媒体文件都没有的条目跳过 |
| 无法识别 | 没有 `item.json`、格式版本不对、路径越出条目文件夹 | 跳过并说明 |

- **冲突的三种处理**：保留本地（只补本地缺的文件）、用导入的（导入的文件校验通过后替换本地的同名文件，再删除本地多余的登记文件）、合并（本地已有的同名文件保留，补上缺的，`parts`、直播段、`live.incidents` 取并集）。可以逐条选，也可以“全部冲突都……”；逐条选的优先，两处都没选的冲突这次跳过。本地条目在另一个作者文件夹时，三种处理都写进本地原来的文件夹，不搬动本地文件。
- **同一场直播的两部分**：两台机器各录到一部分段时，合并把导入的段接在本地段之后、按顺序重新编号（本地文件从不改名），内容相同的段只留一份；导入的直播已经录完而本地的还标着录制中时，按“可补充”更新清单。
- **写入**：文件先复制为 `.part`，校验字节数与 SHA-256 后改正式名，`item.json` 最后写入并更新索引与信息流；中途取消或中断不会留下半个文件，再导入一次会从剩下的继续。默认复制，来源不动；勾选“导入后删除来源里已导入的文件”才删，只删校验并导入成功的文件与变空的文件夹。
- **位置**：导入的条目放在本地当前保存位置的同一相对路径；作者文件夹按 `item.json` 的归属（合作视频的 `via` 等，DEC-056、DEC-061）不变。
- **进度**：扫描与导入都是后台任务，任务页侧栏“导入导出”列出进度、速度与结果摘要（新增、补充、跳过、冲突处理、未传完的条数，没完成的条目与原因）；扫描完等待确认的任务可以从这里“查看预览”回到导入页或“放弃”。任务列表只保留本次运行的。

<a id="export-local"></a>
### 6.4 本地导出

- **资源库导出**：媒体库“⋯ → 导出…”选范围（全部，或媒体库当前的筛选：类型、站点、来源或作者、搜索词）和目标文件夹，按第 6.1 节的格式复制已完成的文件与 `item.json`；只复制 `item.json` 登记的文件，正在缓存、录制中的条目只导出已完成的部分。目标里已有内容相同的文件就跳过，所以中断后再导出一次会接着做。作为后台任务列在任务页“导入导出”。导出的文件夹可以被另一台 TRACE 导入。
- **订阅导出与导入**：订阅页“⋯ → 导出订阅…”写 `trace-subscriptions.json`（填的是文件夹时自动补上这个文件名）（`format: "trace-subscriptions"`、`version: 1`、导出时间、节点、规则、订阅、设置的一部分，与第 4 节的快照相同，不含 Cookie）。“⋯ → 导入订阅…”先预览：新订阅、已在某个订阅里的账号（跳过或合并进已有订阅）、同 ID 但内容不同的规则（保留本地 / 用导入的）。确认后一次写入。

<a id="status"></a>
## 7. 远程状态与本地的“设置 › 远程”

- **状态内容**（`GET status`）：版本与协议、节点名、启动时间、导出目录的剩余与总空间；全部四个站点（哔哩哔哩、抖音、微博、X）的登录状态（有效、需要重新同步、没有 Cookie、退避到某时）、账号昵称、Cookie 同步时间；订阅数、账号数、上次同步时间与快照哈希；每个账号的上次检查时间与结果、下一轮预计时间（同任务页“检查计划”）；正在缓存与排队的任务数，最近 20 条完成与失败；正在录制的场次（主播、开始时间、时长、大小、段数、异常数）；上传方式、排队与正在上传的条目数与字节数、今日已上传、最近一次失败及原因；最近 20 条错误（类别与脱敏后的说明）。不含任何凭证、签名地址与流地址。
- **本地页面**：设置新增分类“远程”（[界面 §3.7](../ui.md#settings)）。没有连接时：粘贴连接码，或分别填地址、令牌、指纹。连接后：状态卡片（在线或无法连接及原因、版本、运行时长、空间）；站点行（登录状态，“同步 Cookie”；点击 X 行“同步 Cookie”先弹出机房 IP 风险确认框）；订阅行（“远程 N 个订阅 · M 个账号 · X 前同步”，本地与远程不同时写“有改动未同步”，“同步订阅”）；录制、缓存、上传、检查与错误各一节，可展开。页面打开时每 30 秒刷新一次，另有“刷新”按钮；页面关闭时不请求远程（前三个站点 Cookie 待同步的后台重试除外）。
- **只连一个远程**：现在只保存一个连接；数据结构按列表设计，以后的集群模式再放开。
- **验证**：`go run ./tools/smoke -server` 在临时目录跑真程序：`init` → 启动 → 用连接码读状态（含四个站点行：`weiboSiteReported`、`xSiteReported`）→ 同步含微博与 X 账号的合成快照 → 用假 rclone 上传一个合成条目并确认本机文件已删 → 停止，并对本地假微博与假 X 接口验证两步 `PushCredential`、非法凭证不覆盖旧登录、订阅同步、按规则自动缓存（不做全部缓存）与哨兵脱敏（`weiboFakeSiteVerified`、`xFakeSiteVerified`），回执在 `artifacts/smoke-server/`。Linux 上用 `SIGTERM` 停止并确认正常退出、数据目录锁已释放；Windows 上没有控制台信号可发，改为结束进程后再启动一次确认锁已释放。冒烟把代理指向本机的空端口，任何站点请求都出不去。CI（Ubuntu）在 `tools/check` 之后跑同一条命令。

<a id="cluster"></a>
## 8. 为集群模式预留

- 节点 ID（每个数据目录一个，随机生成）与名字；`item.json.cachedBy`；状态与快照带节点。
- 导入按条目键合并、与来源无关，所以多台机器的导出可以先后导入同一个资源库，同一条目的不同部分（如两台机器各录到的段）会合并。
- 多台机器分担同一批账号（谁检查哪个、避免重复缓存）还没有做（FR-REMOTE-009）；现在每台远程都独立检查同步给它的全部账号。
