# 技术设计：直播

开播状态、手动与自动录制、录像条目（FR-LIVE-001、FR-LIVE-002，DEC-027）。协议见[协议资料 §20](../research/bilibili.md#live)，录制路线的选型见[订阅、弹幕与直播选型 §3](../research/2026-11-07-subscriptions-live.md#recording)，订阅规则见[订阅设计](subscriptions.md)。

<a id="status"></a>
## 1. 开播状态

- `LiveService.Status(uids)` 用按 uid 批量查询的接口，每次最多 50 个；结果使用 60 秒查询缓存，重复打开页面或直播间不延长缓存期限。
- 刷新时机：打开订阅列表、订阅详情、用户页时（只查当前可见的账号）；每轮检查更新（手动或定时）对这一轮的账号查一次；开播检查器（第 3 节）运行时。
- 订阅网格按虚拟列表的实际可见行收集账号，每批最多 50 个；滚动后补查新头像，订阅详情查询该订阅的账号。界面每账号的查询尝试间隔至少 60 秒，失败不会因重绘立即重试；风控、限流或登录失效停止自动刷新，手动刷新或重新登录后恢复。用户页可查询尚未订阅的账号；可见账号查询不启用自动录制规则。
- 用户页直播查询失败时保留已加载的资料并显示原因；离开页面或切换账号后，迟到的结果与错误不覆盖当前页面。
- 结果 `{uid, roomId, status: "live"|"offline"|"round"|"none", title, cover, liveSince, quality, qualityName, codec}`；`none` 表示没有直播间（不在返回里）。轮播（`round`）按未开播显示，不录制。清晰度名称（`qualityName`）取 `g_qn_desc`，取不到时按 `10000=原画、400=蓝光、250=超清、150=高清、80=流畅` 映射，在用户页直播横幅、订阅详情“直播”标签、任务页录制行与录像详情中统一展示为“原画 · AVC”格式（DEC-033）。
- 可见账号查询的返回值直接更新当前界面；录制状态通过 `live:changed` 更新，主页侧栏的“正在直播”与订阅列表随之更新。

## 2. 录制器（`internal/live`）

**路线（MVP）**：只录 HLS 的 fMP4 流，录完转成普通 MP4。取流结果里没有 `http_hls` + `fmp4` 时，录制失败并说明“这个直播间现在没有提供可录制的流格式”；HTTP-FLV 后备是 [LOOP-004](../delivery/status.md#loop)。加密流（`all_special_types` 含 203）不录，说明原因。

1. **取流**：`getRoomPlayInfo` 请求原画（`qn=10000`）；在 `http_hls` / `fmp4` 下先选 `current_qn` 最高的一路，同画质时再按设置的 `codecOrder` 选择编码（默认 AVC 优先；HEVC 在部分电脑上应用内放不了）。编码偏好不降低画质；`url_info` 里官方节点优先，去掉 `*.mcdn.*`。地址只在内存里。
2. **轮询播放列表**：按 `EXT-X-TARGETDURATION` 的间隔（1～5 秒，夹紧）请求媒体播放列表，播放列表文本上限 1 MiB；按 `EXT-X-MEDIA-SEQUENCE` 只取没取过的分片；`EXT-X-MAP` 的初始化分片每个文件只写一次。
3. **写入**：新段写入前确认正式名与临时名没有用户文件，先把 `part-NNN.mp4.part` 登记到 `item.json.pendingParts`，再写初始化分片与按序号追加 `.m4s`。校验完整分片、`fsync` 后原子保存 `live.pendingFile`、`pendingBytes`、`pendingDuration`、`lastSequence`；只有落盘成功才推进已处理序号。checkpoint 保存只核对已完成媒体的路径/长度，不每次重读既有录像的 hash。
4. **换段**：遇到 `EXT-X-MAP` 地址或内容变化、`EXT-X-DISCONTINUITY`、序号跳空超过 3 个、媒体序号倒退、初始化分片里的编码参数变化、重新取流后：结束当前段、开始 `part-(N+1)`。不在一个文件里拼接不连续的内容。
5. **断流与重连**：分片或播放列表请求失败（网络错误、5xx、403/404/410 地址失效）时，6 秒后重新调用 `getRoomPlayInfo` 取新地址（不复用旧地址）继续；10 秒收不到新分片按断流处理。连续 5 分钟取不到流，或开播状态变为未开播，就结束录制。HTTP 412 或取流遇 -352/-412：按风控立即结束并记原因，不重试；-101：按[架构 §4](architecture.md#bilibili-client)处理并结束。
6. **收尾**：每段用 mp4ff 的 `Defragment` 与磁盘样本读取转成 `moov` 在前的普通 MP4（不把完整录像读入内存，样本数据原样复制）。转换在临时文件里完成，校验视频轨、正时长、与登记分片时长之和误差 ≤ 0.1 秒及 SHA-256 后改成 `part-NNN.mp4`；正式文件/段信息成功写入清单后才删除原 `.part`。转换或清单保存失败保留原文件与待恢复登记，条目部分完成或返回 storage，不能仅凭封面标绿。
7. **关闭应用**：停止所有录制，按第 6 步收尾（关闭钩子限时 30 秒；来不及转换的保留 `.part`）。下次启动只处理库索引中直播清单登记的录制 part，包括已接入的旧根，不扫描或认领任意同名用户文件；当前段先截断 checkpoint 字节数之后的未完成尾部再收尾。已改正式名但清单尚未提交时，按同一登记的确定正式名校验恢复。
8. **空间**：保存位置剩余空间低于 1 GiB 时结束录制，原因 `storage`。

- 录制不占用缓存任务的并发名额，同时录制数取 `maxRecordings`（默认 2）；超过时手动开始返回明确错误，自动录制记在订阅上“已达到同时录制数”。
- 分片下载带 `Referer`/`Origin: https://live.bilibili.com`、公共 UA，不带 Cookie；但取流接口带登录 Cookie，未登录不开始（INV-07）。
- 进度事件每秒至多一次：已录时长、字节数、当前码率、段数、状态（录制中、重连中、收尾中）。

<a id="auto-record"></a>
## 3. 开播检查与自动录制

- 有任何订阅开启“开播自动录制”时，`internal/subscription` 的调度器每 `liveCheckIntervalMin`（默认 3 分钟）查一次这些订阅的全部账号的开播状态（每 50 个一次请求），计入规则请求的每小时额度，遵守退避（[订阅 §3](subscriptions.md#schedule)）；未登录不运行。
- 发现开播且这个账号没有进行中的录制 → 自动开始录制（任务标“自动”）；录制因下播结束后，下次发现开播再开始新的录制。
- 手动停止一场自动录制后，这一场（同一个 `live_time`）不再自动开始。

<a id="recording-item"></a>
## 4. 录像条目

- 条目键 `live:<room_id>:<开播时间 Unix 秒>`；文件夹 `<保存位置>/bilibili/<uid>/lives/<room_id>-<开播时间>/`，里面是 `item.json`、`cover.jpg`、`part-001.mp4`…。同一场录制中途重新开始（手动停止后再开始）用同一个条目，段号接着往下编。
- `item.json` 记录：主播、房间号、直播标题（开始时与结束时的）、开播时间、录制开始与结束时间、每段的文件、字节数、SHA-256、时长、编码、分辨率、画质（`current_qn` 与描述）、结束原因（下播、手动停止、断流超时、风控、空间不足、应用关闭）。不记录流地址。
- 索引、删除、媒体协议与点播条目相同（[数据 §1～§3](data-and-cache.md#storage)）：只有校验通过的正式文件登记为可播放；录制中的条目圆点是进度圆环，正常结束为绿，转换失败或中途风控为黄并写明原因。删除按 INV-09。
- 主页信息流与媒体库把录像当作一种条目（[数据 §4](data-and-cache.md#feed)）；播放时多段按段列出，依次播放。
