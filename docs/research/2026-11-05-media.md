<a id="mux"></a>
## 1. 合并 DASH 音视频

哔哩哔哩的播放地址给的是 DASH：视频流和音频流分开，各是一个带 `sidx` 的分片 MP4（`.m4s`），需要合成一个文件才能直接播放。

| 方案 | 证据 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **纯 Go：`github.com/Eyevinn/mp4ff`（默认，Q-003）** | MIT；v0.62.0 发布于 2026-11-04，前两版 2026-10-27、2026-10-13；专注分片 MP4 与 DASH；`mp4` 包里有 `elst`/`edts`（编辑列表）、`dfLa`（FLAC）、`dac3`/`dec3`（AC-3/E-AC-3）等盒子的读写 | 不带外部程序，包体几乎不增加；在 Go 进程内完成，便于测试和报错 | 拼装、交错和编辑列表要自己写；杜比与无损音轨的合并要实测 |
| 随包附带 ffmpeg（LGPL 构建） | Windows 构建 `win64-lgpl` 静态包约 160 MiB（压缩），共享库版约 73～78 MiB；需要附带许可说明和源码获取方式 | 兼容性最好，以后转码、截图都能用 | 包体增加最多；多一个外部进程和许可义务 |
| 不合并，保留两个流 | — | 最简单 | 系统播放器打不开，不可接受 |

**输出格式要求**（与常见下载工具的输出对齐，方便系统播放器和剪辑软件使用）：

- 渐进式 MP4：`ftyp` + `moov` 在前（快速开始）+ `mdat`；品牌 `isom`/`mp42`。
- **交错存放**：音视频样本按约 1 秒一块交替写入 `mdat`，`stco`/`co64` 指向各块；不要每条轨一整块（那样播放和拖动时读取位置在文件两端来回跳）。
- **编辑列表**：源流的 `elst` 与合成时间偏移要带到输出里（例如视频首帧的 `ctts` 偏移），保证音画同步，且各轨时长与源流一致（误差不超过一帧）。
- 每个分 P 一个文件；校验见[数据设计 §2](../design/data-and-cache.md#cache)。

来源：[mp4ff 仓库](https://github.com/Eyevinn/mp4ff)、[mp4ff 发布](https://github.com/Eyevinn/mp4ff/releases)、[pkg.go.dev 版本](https://pkg.go.dev/github.com/Eyevinn/mp4ff?tab=versions)、[FFmpeg Windows 构建发布页](https://github.com/BtbN/FFmpeg-Builds/releases/latest)。

<a id="hires-audio"></a>
### 1.1 最高音质（杜比全景声、Hi-Res 无损）

账号能拿到时，播放地址的 `dash.dolby.audio[]`（E-AC-3，代码 30250）和 `dash.flac.audio`（FLAC，代码 30251）比普通音频（最高 192K）音质更高（[协议资料 §14](bilibili.md#playurl)）。按 DEC-024 默认取最高档：

- `mp4ff` 支持 FLAC（`fLaC`/`dfLa`）盒子的读写，但这不证明特定 MP4 里的 FLAC 能被 Media Foundation 读取；本次没有真实 FLAC-in-MP4 解码证据。
- 杜比全景声（E-AC-3，`ec-3`/`dec3`）依赖客户机的解码能力。M1 按 Q-005 与计划 PR-2 的后备边界实现：**FLAC（30251）与杜比（30250）最高音轨均原样另存为 `Pxx.audio-<代码>.m4a`，主 `Pxx.mp4` 合并同分 P 最好的普通 AAC**，清单记录实际档位与 `savedAs`。最高轨存在而 AAC 缺失/失败时保留最高轨并报告失败/缺失，不生成静音的完成主视频；相关合成回归入口见阶段报告 F-017。后续取得真实 FLAC-in-MP4 解码证据后再决定直接合并。

## 2. 缓存索引数据库

媒体库、主页信息流要按作者、时间筛选排序和双向翻页，任务要在重启后恢复，条目可能上万，JSON 文件不合适。

| 方案 | 证据 | 取舍 |
| --- | --- | --- |
| **`modernc.org/sqlite` v1.61.1（选定）** | BSD-3-Clause；v1.61.1 发布于 2026-10-31，前两版 2026-10-21、2026-09-29；纯 Go，不需要 cgo | 本机没有 C 编译器，纯 Go 驱动可以直接用。包很大，首次编译慢，之后有构建缓存 |
| `github.com/ncruces/go-sqlite3` | 用 WebAssembly 运行 SQLite，同样不需要 cgo | 选定方案满足需求 |
| cgo 驱动 | 需要 C 编译器 | 不选 |

数据库只做索引，正本是每个条目文件夹里的 `item.json`，所以数据库坏了可以重建（NFR-DATA-002）。

来源：[pkg.go.dev 版本](https://pkg.go.dev/modernc.org/sqlite?tab=versions)、[许可](https://pkg.go.dev/modernc.org/sqlite?tab=licenses)。

## 3. 在原生界面内播放本地视频、显示本地图片（DEC-032）

改为 `mygo/ui` 原生界面后，不再使用 WebView2 自定义协议 `trace-media://`。所有本机媒体访问先过 `Library.MediaPath(key, relPath)` 白名单校验（INV-08：只允许索引登记、位于条目文件夹内的文件，拒绝 `..`、绝对路径、符号链接/目录联接与跨条目访问）。

### 3.1 视频与音频播放（`internal/player`）

查验 `github.com/egoist/mygo@v0.8.1` 的 `ui/video.go` 与 `audio/audio.go`：

- `mygo/ui` 内建的 `ui.Video` 目前只注册了 GIF 解码器，没有音轨时钟。
- `mygo/audio` 在 Windows 上使用 WASAPI 播放任意实现 `audio.Decoder`（`SampleRate() int`、`Channels() int`、`Read([]float32) (int, error)`、`SetPosition(int64) error`、`Len() int64`）的音源，并提供精确的播放时钟 `Player.Position()`、`Seek(d)`、`Pause()`、`Play()`、`SetVolume(v)`。
- `mygo/ui` 提供动态位图 `c.Bitmap(w, h)`（`bitmap.Update(rgba)` 零拷贝上传纹理到 GPU）与 `c.Animate` 帧循环。

因此在 Windows 上，应用内 MP4 播放选型对比如下：

| 方案 | 证据 | 取舍 |
| --- | --- | --- |
| **Windows Media Foundation（`IMFSourceReader`）+ `mygo/audio` + `*ui.Bitmap`（选定）** | Windows 10/11 系统自带 `mfplat.dll`、`mfreadwrite.dll`、`ole32.dll`；用 `golang.org/x/sys/windows`（`NewLazySystemDLL` + COM 虚表调用，`CGO_ENABLED=0`）创建 `MFCreateSourceReaderFromURL`，开启 `MF_SOURCE_READER_ENABLE_ADVANCED_VIDEO_PROCESSING` 将视频帧解为 `MFVideoFormat_RGB32` 写入 `*ui.Bitmap`，音频轨解为 `MFAudioFormat_Float`（或 PCM 16-bit 转 `float32`）喂给 `mygo/audio` 的 `Player`，以音频播放位置 `Player.Position()` 为主时钟同步视频帧，`SetCurrentPosition` 实现拖动（Seek） | 零外部二进制体积、零 cgo、不带百兆 ffmpeg；原生支持 AVC/AAC/FLAC（系统装有扩展时也支持 HEVC/AV1）；同時在播放层顶部提供“用系统播放器打开”按钮作为兜底 |
| 随包附带 ffmpeg / libmpv DLL | 体积增加 70～160 MiB，且涉及动态库分发与许可合规 | 不选 |
| 只调用外部系统播放器 | 无法在应用内叠加弹幕、字幕和拖动控件（违反 FR-LIB-002、FR-LIB-004） | 不选 |

原型 **PR-1** 与默认测试验证合成 AVC+AAC 小样本的视频帧/音频采样读取、Seek 时间戳和静音时钟。测试注入静音输出，不验证真实设备出声；大于 2 GiB 的 `co64` 门控、真实 HEVC/AV1/FLAC 媒体及用户音频体验不能由小样本通过推导，执行状态见[阶段报告](../delivery/stage-report.md)与 H-001。

## 5. 下载稳定性

2026-11-04 实测：用登录 Cookie 下载一条约 6 MB 的视频流时，CDN 在发出 524,288 字节（512 KiB）后关闭了连接。哔哩哔哩的媒体地址常常指向不同类型的节点（`upos-*` 官方节点、`*.mcdn.bilivideo.cn` 等 PCDN 节点，见[协议资料 §15](bilibili.md#media-cdn)）。

TRACE 的做法：

| 做法 | TRACE |
| --- | --- |
| 分段 `Range` 请求（固定块大小），每段单独校验 `206` 与 `Content-Range` | 采用：每段 8 MiB |
| 段内提前断开、超时、连接重置、5xx：自动重试，指数退避 | 采用：每段最多 5 次（1、2、4、8、16 秒，带随机抖动），失败的那段从已写入的位置续传 |
| 在主地址与备用地址之间轮换 | 采用：先试官方节点，再试 PCDN 节点；同一地址连续失败就换下一个 |
| 地址过期（403/404/410）时重新取播放地址 | 采用：每个分 P 最多重取一次 |
| 遇到风控（412）不重试 | 采用：立即暂停任务并说明原因 |

自动重试只针对媒体文件的传输错误；API 请求（动态列表、播放地址等）仍然不自动重试（[协议资料 §12](bilibili.md#pacing)）。
