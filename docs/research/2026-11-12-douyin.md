## 1. `a_bogus` 签名实现路线选型

### 1.1 签名职责边界与算法模块拆解

抖音 Web 端接口（如作品详情、用户投稿分页、直播间 Web 进入接口）在查询参数上附加 `a_bogus` 请求签名，将请求查询串、POST 请求体、浏览器 `User-Agent`、屏幕与平台指纹串、页面标识（`page_id`）、应用标识（`aid`，Web 常为 `6383`）与毫秒时间戳混合密封（`源码阅读`，本机参考索引中的抖音签名与访问上下文实现，2026-11-12；当前线上各端点对不同版本签名的实时校验严格度为 `unknown`）。

从公开研究与本机参考索引只读分析可见，`a_bogus` 存在两代常见参数形态（`源码阅读`，2026-11-12）：

1. **早期 `cus` 形态**：盐值 `"cus"`，4 字节随机头 + 19 槽位载荷 + 256 字节置换表流变换，部分直播间 Web 接口实现仍沿用此形态（线上是否继续接受为 `unknown`）。
2. **现行 `bdms.js`（如 `v1.0.1.19-fix.01`）`dhzx` 形态**：盐值 `"dhzx"`，Web 常见 `aid = 6383`、`page_id = 6241`，头部魔数 `(3, 82)`，载荷密钥 `0xD3`，双周纪元起点 `1721836800000`（`2024-07-24T16:00:00Z`）。其完整运算仅依赖四类确定性原语，不含非对称密码或硬件绑定指令：
   - **SM3 密码杂凑（GB/T 32905-2016）**：对 `query + salt` 与 `body + salt` 分别执行两次 SM3（`SM3(SM3(msg))`）；对 `User-Agent` 低字节流先经 `key = [0, 1, 14]` 魔改 RC4 变换并按自定义 Base64 字母表 A 编码后执行一次 SM3；每条摘要链在载荷中写入 2 个原文字节与 1 个避开哨兵值的校验字节（canary byte）。
   - **魔改 RC4 与双自定义 Base64 字母表**：256 字节 S 盒按倒序初始化（`box[255-i] = i`），密钥调度采用乘法混合 `j = (j*box[i] + j + key[i%len]) & 0xff`，伪随机流生成阶段与标准 RC4 一致；Base64 仅替换两套重排 64 字符映射表（字母表 A 用于密封 UA，字母表 B 用于最终输出 `a_bogus`）。
   - **50 标量槽位重排与异或校验和**：按固定置换表排列 50 个单字节槽位（含 6 字节毫秒时间戳、时间戳减 1 派生值、双周纪元计数、三条 SM3 摘要链采样位、`page_id`、`aid`、4 字节 SDK 版本与环境探针标志位、屏幕平台指纹串如 `"1920|947|1920|1032|1920|1032|1920|1080|Win32"` 及其字节长度），并对 8 字节掩码版本头 + 50 槽位计算单字节 XOR 校验和。
   - **可逆位掩码噪声展开**：内层采用 `3 -> 4` 互补掩码拆分（噪声掩码 `(0x91, 0x42, 0x2C)` 与数据掩码 `(0x6E, 0xBD, 0xD3)` 按位互补，异或恒为 `0xFF`），外层版本头采用 `2 -> 4` 奇偶位交替掩码（`0xAA` / `0x55`），其中版本头的 3 个噪声字节分别编码浏览器家族数值带（如 Chrome `0..39`、Edge `125..164`）与 SDK 环境位掩码（`0xB2`）。

此外，抖音部分高风控端点还会伴随检查页面下发的 `__ac_nonce` / `__ac_signature`（纯位运算与字符串哈希），或基于 Cookie `uifid` 的两阶段请求保护——在拼入 `a_bogus` 后按序追加可选 `verifyFp`/`fp`、`uifid` 与秒级 `timestamp` 重序列化查询串，计算 32 位小写十六进制 `MD5(uifid_timestamp_salt_query)`（Go 标准库 `crypto/md5` 即可计算），将其同时作为尾随查询参数与同名请求头 `x-secsdk-web-signature` 发送，并伴随请求头 `uifid` 与 `x-secsdk-web-expire`（`源码阅读`，本机参考索引中的抖音签名与访问上下文实现，2026-11-12；详见 `docs/research/douyin.md` §2.2）。因此签名层接口不能写死为“输入 URL 输出单个查询参数”，而应统一抽象为“输入请求上下文，输出最终完整编码查询串与附加请求头”。

#### 1.2.4 纯 Go 路线的确定性测试向量设计

由于 `a_bogus` 在外层混入了随机数（`3 -> 4` 噪声位与头部 3 个噪声字节），直接调系统时钟与真随机源会导致每次输出字符串不同。固定测试向量采用**双层锁定策略**（`源码阅读` + `本机合成样本原型验证`，2026-11-12）：

1. **注入确定性时钟与随机源（逐字节黄金向量锁定）**：在 `SignInput` 中注入 `Now time.Time`（固定合成毫秒时间戳，如 `1760000000123`——同时注意为“载荷尾长模 3 余 2 且单字节 XOR 校验和恰好为 `0x00` 时末尾零字节被省略”这一约 `1/690` 概率的编码边界单独构造一条回归向量）与 `Entropy io.Reader`（测试传入固定字节流如 `bytes.NewReader(...)`），即可在 `go test` 中 `100%` 逐字符锁定输出字符串，防止重构改坏任何一位掩码。
2. **编写逆向结构解码器（跨实现与真实样本预言机校验）**：利用数据掩码 `(0x6E, 0xBD, 0xD3)` 与噪声掩码 `(0x91, 0x42, 0x2C)` 严格互补的性质，在 `*_test.go` 中实现 `decodeABogus(sig, query, body, ua)`（自定义字母表 B Base64 解码 → `0xD3` 魔改 RC4 解密 → 解掩码 8 字节头 → `4 -> 3` 剥离噪声还原 50 标量槽位 + 尾部屏幕平台指纹串 + XOR 校验和 → 重新计算三条 SM3 链比对采样字节与校验字节）。该解码器不依赖随机数种子：既能验证任意随机噪声下生成的签名内部结构 100% 自洽，也能在获得用户授权的本地真实检查（存放在被 Git 忽略的 `.local/`）时，直接解码浏览器原生生成的 `a_bogus` 样本以核验 `aid`、`page_id`、4 字节 SDK 版本字段与摘要盐值是否发生线上变更。

### 1.5 三路线综合对比、推荐决策与 `Signer` 接口边界

| 评估维度 | 路线 (a)：自研纯 Go 原生实现（**推荐主路线**） | 路线 (b)：`dop251/goja` 纯 Go JS 引擎 | 路线 (c)：`wazero` + `quickjs-ng` WASM（**架构备选**） |
| --- | --- | --- | --- |
| 新增 Go 模块依赖 | **0 个**（SM3 按 GB/T 32905-2016 自写约 80 行） | 5 个（`goja` + `regexp2` + `sourcemap` + `pprof` + `x/text`） | 1 个 Go 模块（`wazero`）+ 1 个 `.wasm` 静态资产 |
| 版本锁定稳定性 | 随仓库源码版本化 | 无 semver 标签，只能锁伪版本 | `wazero v1.12.0` + `quickjs-ng v0.18.0` 均有正式 Release |
| `CGO_ENABLED=0` 兼容 | 原生纯 Go，无 JIT 内存页依赖 | 原生纯 Go | 原生纯 Go；`windows/amd64` 实测支持 Compiler 与 Interpreter |

#### 推荐结论与切换边界

1. **主路线选定：路线 (a) 自研纯 Go 原生实现（内置约 80 行标准 SM3，零新增外部依赖）**。
   - 理由：零依赖、`+0 KiB` 体积增量、微秒级无锁执行、确定性双层测试（固定种子黄金向量 + 逆向结构解码器），且彻底规避专有 JS 脚本分发版权问题与伪造 DOM 被静默投毒的隐患。
2. **备选路线选定：路线 (c) `tetratelabs/wazero` + `quickjs-ng` WASI（优于 `goja`，M3 暂不引入）**。
   - 理由：实测 `goja` 仅空载引入即膨胀 `+9.65 MiB` 且无语义化发版标签；若未来后续迭代确实出现需要在受控内存沙箱中运行外部干净脚本的场景，`wazero`（`+1.31 MiB`）+ `qjs-wasi-reactor.wasm`（`+1.49 MiB`）体积仅为 `goja` 的 `29%`、支持 ES2023 且具备 WASM 线性内存隔离。但在 M3 阶段**不预装**任何 JS/WASM 引擎；若线上签名突发改版，按[来源与安全 §2](../dev-rules/sources-and-safety.md#site-rules)如实报告签名/风控阻断并暂停任务、不自动重试，记入 `USER-ACTIONS.md` S 项，待更新纯 Go 实现后发版修复。
3. **统一切换接口设计（`internal/site/douyin`）**：
   将签名器封装为与具体执行后端无关的 Go 接口，使上层 HTTP 客户端、分页器与直播客户端完全不感知底层是纯 Go 还是未来的 WASM 备选：

   ```go
   type SignInput struct {
       Endpoint    string    // 规范化路径，如 "/aweme/v1/web/aweme/post/" 或 "/webcast/room/web/enter/"
       Query       string    // 按实际发送顺序编码好的查询串（不含 a_bogus）
       Body        []byte    // 请求体（GET 传 nil）
       UserAgent   string    // 必须与最终 HTTP 请求头 User-Agent 逐字符一致
       BrowserInfo string    // 屏幕与平台指纹串
       PageID      uint32    // 页面标识（如 Web 6241）
       AID         uint32    // 应用标识（如 6383）
       UIFID       string    // 可选 Cookie uifid，用于按端点策略生成两阶段伴随查询参数与请求头
       VerifyFp    string    // 可选指纹（来自 Cookie s_v_web_id），用于伴随签名重序列化追加 verifyFp/fp
       Now         time.Time // 注入墙钟，单测时固定毫秒值
       Entropy     io.Reader // 注入随机源，单测时传入确定性字节流
   }

   type SignResult struct {
       QueryParam  string            // 主签名参数名，默认为 "a_bogus"
       Signature   string            // 生成的 a_bogus 原始签名字符串（供诊断与解码校验）
       SignedQuery string            // 拼好 a_bogus 及可选 verifyFp/fp/uifid/timestamp/x-secsdk-web-signature 后的完整编码查询串，避免调用方二次拼接导致 MD5 原像失配
       Headers     map[string]string // 可选伴随请求头（如 uifid、x-secsdk-web-signature、x-secsdk-web-expire）
   }

   type Signer interface {
       Sign(ctx context.Context, in SignInput) (SignResult, error)
   }
   ```

   **跨实现测试向量复用方式**：测试集保存为纯数据 JSON 夹具（记录 `SignInput`、固定随机字节序列、期望输出以及结构解码期望字段 `aid`/`page_id`/毫秒时间戳/三条 SM3 链校验结果）。纯 Go 实现同时断言“固定随机源下的逐字符相等”与“任意随机源下的 `decodeABogus` 结构自洽”；若未来挂载备选实现，无需重写测试，直接拿同一组 `SignInput` 跑 `decodeABogus` 结构契约测试即可验证输入摘要链、时间戳与环境位完全一致。

## 2. 直播录制路线选择与跨站（抖音 + 哔哩哔哩 `LOOP-004`）共用分析

### 2.1 抖音直播主路线：HTTP-FLV 优先，HLS-TS 作为受控后备

查阅本机参考索引中的抖音直播录制与多平台无界面录制实现可见，抖音直播房间信息（如 `stream_url.live_core_sdk_data.pull_data.stream_data` 及 `flv_pull_url` / `hls_pull_url_map`）按清晰度档位（`origin` 原画、`uhd` 蓝光、`hd` 超清、`sd` 高清、`ld` 标清、`ao` 音频流）分别给出 `main.flv` 与 `main.hls` 地址，并在 `sdk_params` / `extra` 中标注编码（`h264` 或 `h265` / `bytevc1`）（`源码阅读`，2026-11-12；真实线上不同房间的档位分布待授权检查验证）。

| 对比维度 | **HTTP-FLV（推荐主路线）** | **HLS-TS（推荐后备路线）** |
| --- | --- | --- |
| 原画（`origin`）可得性 | 原画档普遍优先且稳定在 `main.flv` / `flv_pull_url` 提供；部分网页内嵌状态路径仅能解析出 FLV 拉流表而 `hls` 字段为空（`源码阅读`，2026-11-12） | 部分房间缺少原画档或仅提供转码档；少数电台/移动端转推场景可能仅暴露 `.m3u8`（`源码阅读`，2026-11-12） |
| 封装形态（与 B 站差异） | 连续 FLV Tag 字节流（`TagType` 8 音频 / 9 视频 / 18 脚本） | **注意**：不同于哔哩哔哩主路线的 **HLS-fMP4（`.m4s`）**，抖音 HLS 普遍为 **MPEG-TS（`.ts`）** 分片——无法像 B 站那样把分片原样追加后直接 `mp4.Defragment`，同样必须经过解复用与样本重组 |
| 连接与请求节奏 | 单条 HTTP 长连接顺序读取，首帧延迟低，无周期轮询开销，不会因轮询抖动滑出 m3u8 窗口丢片 | 需每 1～3 秒轮询 `.m3u8` 并逐个请求 `.ts` 分片，请求频次高，网络抖动时易出现 `EXT-X-MEDIA-SEQUENCE` 跳空 |
| 选流防坑边界 | 必须检查 URL 查询参数是否含 `only_audio=1`（`ao` 纯音频流常与原画同源仅多此参数），防止误把纯音频流当作视频流录制；存在双屏流 `pull_datas` 时默认取主画面 `live_core_sdk_data`（`源码阅读`，2026-11-12） | 同左，且需处理 `.m3u8` 嵌套 Master Playlist 与 `#EXT-X-DISCONTINUITY` |

**路线决策**：

1. **抖音直播录制主路线采用 HTTP-FLV**：按清晰度优先级（默认最高画质 `origin -> uhd -> hd -> sd -> ld`，排除 `only_audio=1` 除非房间明确为纯音频电台直播）选择 `flv` 拉流地址，经实时解复用写入分段 fMP4（`.mp4.part`）并在结束后 `mp4.Defragment` 输出普通 MP4。
2. **HLS-TS 后备触发条件**：仅当 (a) 目标房间所有非纯音频清晰度档均只有 `hls` 地址而无 `flv` 地址，或 (b) 当前录制的 HTTP-FLV 地址在流未下播的前提下短时间内连续发生非风控传输中断（例如 60 秒内连续 3 次非正常 EOF/连接重置）且重取流地址后仍复现时，录制器结束当前分段文件并新开分段切换到 HLS-TS。关于 HLS-TS 后备在 M3 首版立即交付还是先完成 HTTP-FLV 主路线再按真实验证情况接入，见 §3.1 与 §3.4 的依赖增量权衡供 A 拍板。

### 2.2 与哔哩哔哩 HTTP-FLV 后备（`LOOP-004`）共用同一管线的分析

核查仓库现有 [`internal/site/bilibili/live.go`](../../internal/site/bilibili/live.go) 实现（`源码阅读`，2026-11-12）：`(c *Client) LiveRoomPlayInfo` 请求 `getRoomPlayInfo` 时已携带 `protocol=0,1&format=0,1,2&codec=0,1,2`（第 242–244 行），服务端同时返回 `http_hls`（`fmp4` / `ts`）与 `http_stream`（`flv`）；当前该函数内置的候选筛选循环仅保留 `pName == "http_hls"` 且 `fName == "fmp4"`，当少数直播间未返回 `fmp4` 候选时直接返回 `&SiteError{Kind: ErrKindUnavailable, Message: "这个直播间现在没有提供可录制的 HLS fMP4 流格式"}`（第 398–403 行，即[交付状态](../delivery/status.md#loop)登记的 `LOOP-004`）。

两站 HTTP-FLV 流的异同与抽象边界对比如下（`源码阅读`，仓库 `internal/site/bilibili/live.go` 及本机参考索引中的 B 站 FLV 录制、抖音直播录制与多平台录制实现，2026-11-12）：

| 维度 | 抖音 HTTP-FLV | 哔哩哔哩 HTTP-FLV（`LOOP-004`） | 共用管线处理策略 |
| --- | --- | --- | --- |
| 视频编码封装 | H.264（`CodecID=7`）；H.265（国内非标 `CodecID=12` 或 Enhanced FLV FourCC `hvc1`）；常见 B 帧（正/负 `SI24` CTS） | 完全相同：`codec_name="avc"`（`CodecID=7`）与 `"hevc"`（国内 CDN 普遍发 `CodecID=12`，部分新版推流发 Enhanced `hvc1`）；常见 B 帧 | **100% 共用**同一套双兼容 FLV 视频 Tag 解析器（同时支持 `7`、`12` 与 Enhanced `IsExHeader + hvc1/avc1`） |
| 音频编码封装 | 主流为 AAC（`SoundFormat=10`，`AudioSpecificConfig` + 裸帧） | 主流为 AAC（`SoundFormat=10`） | **100% 共用**；若遇非 AAC（如极端老旧推流 MP3 `SoundFormat=2`）返回明确不支持原因 |
| `onMetaData`（Tag 18） | 键值随推流端 SDK 变化，宽高/码率可能滞后或缺省 | 连麦/PK 切换时 `onMetaData` 常滞后或含自定义字段 | **一律不依赖 `onMetaData` 建轨**：宽高、帧率、采样率与通道数完全从 `avcC`/`hvcC`/`AudioSpecificConfig` 二进制头实解 |
| 流内参数变更与跳变 | 主播切分辨率/旋转画面、静音期单轨先行、CDN 切源导致时间戳跳变 | 连麦/PK/OBS 重推常在**不断开 TCP 连接**的情况下重发不同分辨率的 `SequenceHeader`，或时间戳突变回 0 | **100% 共用**“有效参数集字节指纹比对 + `>10s` / `<-1s` 跳变检测 → 立即收尾当前分段并新开下一分段文件”规则 |

### 3.2 本机合成样本原型验证与 MP4 落盘路线对比

#### 3.2.1 合成样本原型验证记录（2026-11-12）

在独立临时模块 `tmp/m3-proto-check/`（环境：`go1.27.3 windows/amd64`、`$env:CGO_ENABLED="0"`，验证完毕后已删除整个临时目录）执行 `go test -v -count=1 ./...`（总耗时 `0.596s`），构造纯内存合成字节流完成以下四项实测（`本机合成样本原型验证`，2026-11-12）：

1. **FLV（AVC + AAC + 32-bit 时间戳跨界回绕 + 有符号正负 CTS + 尾部残缺 Tag 崩溃截断）→ fMP4 → `mp4.Defragment`**：
   - 构造 FLV 头 + 起始时间戳 `0xFFFFFFC0`（距 `2^32` 溢出仅 64 ms）的 AVC `SequenceHeader`（640×360 SPS/PPS）与 AAC-LC 48kHz 双声道 `AudioSpecificConfig`，写入 6 组跨越 `0xFFFFFFFF -> 0x00000002` 边界的 IDR/P 帧（带 `+33 ms`、`+66 ms`、`-33 ms` 24-bit 有符号 CTS 偏移）与 AAC 裸帧，并在文件末尾故意追加 7 字节残缺半截 FLV Tag 模拟断电。
   - 实测结果：扫描器精确识别并丢弃末尾 7 字节残缺 Tag，完整恢复前 14 个有效 Tag，32-bit 回绕平滑展开为连续单调时间轴（`0..165 ms`），经 `mp4ff` 写出 `.mp4.part` 后调用 `mp4.DecodeFile(..., DecModeLazyMdat, DecStartOnMoof)` + `mp4.Defragment`（并附加仿照点播 `internal/download/mux_disk.go` `addProgressiveEdits` 编写的原型辅助检查验证 `stco -> co64` 偏移重算）产出普通 MP4；重新解码校验确认 `!IsFragmented()`、`moov` 位于 `mdat` 之前、轨道编码盒为 `[avc1 mp4a]`。
2. **国内非标 `CodecID=12` HEVC 与标准 Enhanced FLV `hvc1` 双格式兼容验证**：
   - 分别构造 (a) `0x1c`（`CodecID=12`）+ `HEVCDecoderConfigurationRecord`（1920×1080 Main Profile VPS/SPS/PPS）+ IDR/TRAIL 帧，以及 (b) Enhanced FLV `0x90`（`PacketTypeSequenceStart` + `"hvc1"`）、`0x91`（`PacketTypeCodedFrames` + `"hvc1"` + 3 字节 `SI24` CTS `+33 ms`）与 `0xa3`（`PacketTypeCodedFramesX` + `"hvc1"`，无 3 字节 CTS）。
   - 实测结果：统一解析函数准确区分两种封装及 `CodedFrames` / `CodedFramesX` 的 3 字节偏移差异，经 `SetHEVCDescriptor("hvc1", ...)` 与 `Defragment` 均产出合法 `hvc1` 渐进式 MP4。
3. **MPEG-TS（H.264 Annex-B + ADTS AAC）解复用 → fMP4 → `mp4.Defragment`**：
   - 用 `mediacommon/v2/pkg/formats/mpegts.NewWriter` 生成含 PAT/PMT 与 PES 包的合成 TS 流，经 `&mpegts.Reader{R: ...}` + `Initialize()` + `TimeDecoder` 解出 Annex-B 访问单元与 AAC 裸帧，由 `h264.AVCC(au).Marshal()` 转为 4 字节长度前缀写入同一套 fMP4 分片与 `Defragment` 收尾函数，实测产出 `moov` 在前的 `[avc1 mp4a]` 普通 MP4。
4. **流内 SPS 分辨率变化检测**：
   - 构造 `640×360` 与 `320×180` 两组 `AVCDecoderConfigurationRecord`，验证归一化字节比对可确定性触发分段切分。

#### 3.2.2 “直接写渐进式 MP4” vs “实时写 fMP4 分片复用现有 `mp4.Defragment`”对比

| 评估维度 | 方案 M1：录制中直接写渐进式 MP4（结束时写 `moov`） | **方案 M2（选定）：录制中按 GOP 实时写 fMP4（`part-%03d.mp4.part`）+ 收尾复用 `finalizeLivePart`（`mp4.Defragment`）** |
| --- | --- | --- |

### 3.3 五大核心媒体技术点工程拆解

#### 1. H.264 / H.265 / AAC 配置提取、NALU 长度前缀归一化与流内参数变更分段

- **参数集提取与安全校验**：
  - **AVC (`avc1`)**：从 FLV `AVCPacketType == 0` 解码 `avc.DecodeAVCDecConfRec`（或从 TS 首组 Annex-B `NALUTypeSPS=7` / `NALUTypePPS=8` 提取），必须校验 `len(SPSnalus) > 0 && len(PPSnalus) > 0` 且 `avc.ParseSPSNALUnit` 成功后再建轨。**易错细节**：读取 `lengthSize := int(dcr.LengthSizeMinusOne&0x03) + 1`（允许推流端发 1/2/4 字节长度前缀），在解出每个 NALU 后统一重写为 **4 字节大端长度前缀**（`mp4ff` 默认 `LengthSizeMinusOne = 3`），剔除冗余填充字节与重复内联的 SPS/PPS（已存入 `avc1` 样本入口的 `avcC`）。
  - **HEVC (`hvc1`)**：从 FLV `PacketType == 0` 解码 `hevc.DecodeHEVCDecConfRec`（或从 TS 提取 `VPS=32`、`SPS=33`、`PPS=34`），**强制前置校验 `len(vps) > 0 && len(sps) > 0 && len(pps) > 0`**（规避 §3.1.1 实测发现的 `mp4ff` `SetHEVCDescriptor` 空切片越界 panic），同样将 NALU 长度前缀归一化为 4 字节。
  - **AAC (`mp4a`)**：从 FLV `AACPacketType == 0` 调用 `aac.DecodeAudioSpecificConfig`（或从 TS `CodecMPEG4Audio.Config` 读取 `ObjectType`、`SampleRate`、`ChannelConfig`）写入 `SetAACDescriptor`。
- **起录同步与单轨兜底**：连接建立后先缓冲至收齐首个视频关键帧（含有效视频 SequenceHeader）与音频 SequenceHeader 再写出 `InitSegment`（`ftyp+moov`）；若流本身是纯音频电台或等待满 `3 秒` 仍只有单视频轨（主播闭麦未推音轨），则按实际到达的单轨建 `InitSegment`，避免无限死等。
- **中途参数变更切分**：记录当前分段生效的归一化 `(videoCodec, vps, sps, pps)` 与 `(audioObjectType, sampleRate, channelConfig)` 字节快照。流中再次收到 SequenceHeader 时：若核心参数字节完全一致（CDN 常规重发），静默忽略；**一旦任意参数集字节发生变化（如连麦/PK 切换分辨率、帧率或采样率）**，立即刷盘当前缓存 GOP、`fsync` 并调用 `finalizeLivePart` 收尾当前分段，随后递增 `partIndex` 创建新 `.mp4.part` 写入新 `InitSegment`，绝不在同一 MP4 轨内混写不同参数集。

#### 2. 32-bit FLV 时间戳回绕、有符号 24-bit `CompositionTime` 与乱序/跳变修正

- **32-bit 毫秒时间戳展开**：FLV Tag 头由 `b[4..6]`（低 24 位大端）与 `b[7]`（高 8 位扩展字节）拼成 `rawTS := uint32(b[4])<<16 | uint32(b[5])<<8 | uint32(b[6]) | uint32(b[7])<<24`：
  - **无符号 32-bit 回绕（约 `49.71 天`）**：当 `prevRaw > 0xFFFF0000` 且 `rawTS < 0x00010000` 时，`wrapOffset += (1 << 32)`。
  - **有符号 31-bit 编码器溢出回绕（约 `24.85 天`）**：部分推流器以有符号 `int32` 累加毫秒并在 `0x7FFFFFFF` 溢出归零（而非进入 `0x80000000`）；当 `prevRaw` 位于 `[0x7FFF0000, 0x80000000]` 且 `rawTS < 0x00010000` 时，`wrapOffset += 0x80000000`。
- **有符号 24-bit `CompositionTime`（`SI24`）符号扩展**：FLV 视频包头中的 `CTS` 是有符号补码，存在 B 帧重排时会出现负偏移（`PTS < DTS`）。读取时必须按 `u := uint32(b[0])<<16 | uint32(b[1])<<8 | uint32(b[2]); if u&0x800000 != 0 { u |= 0xff000000 }; ctsMs := int32(u)` 扩展符号位，乘以 `90` 换算为 `90000 Hz` 下的 `int32` `CompositionTimeOffset` 交给 `mp4ff`（存在负值时 `mp4ff` 自动生成 version 1 `trun` / `ctts`）。
- **单调化与断层分段**：
  - 首包到达时记录公共起点 `originMs`，将相对时间归零 `relMs = (wrapOffset + int64(rawTS)) - originMs`。
  - **微小负向抖动夹紧**：同一轨道若出现 `-1000 ms <= relMs - prevTrackMs <= 0`（推流端毫秒取整抖动或音画交错微调），夹紧为单调递增（视频 `dts90 = max(dts90, prevVDTS90 + 90)`，音频按采样点数累加或夹紧），防止 `mp4ff` 生成 `Dur == 0` 或负时长样本。
  - **大跳变切分**：若任一轨出现 **`relMs - prevTrackMs > 10_000 ms`（正向跳空超 10 秒）或 `< -1_000 ms`（反向回退超 1 秒）**，判定为推流重启或 CDN 源切换断层，立即收尾当前分段并在下一视频关键帧开启新分段文件（与[直播设计 §2](../design/live.md#recorder) 的 `EXT-X-DISCONTINUITY` 切分契约完全对齐）。
  - **时钟精度换算**：视频轨固定 `timescale = 90000`（`dts = uint64(relMs) * 90`）；音频轨 `timescale = sampleRate`（如 `48000` 或 `44100`），使用 `mulDiv(relMs, sampleRate, 1000)` 避免整除截断造成长时音画累计漂移。

#### 3. 国内非标 FLV HEVC（`CodecID == 12`）与标准 Enhanced FLV（`hvc1`）双兼容状态机

单字节首部判别 `isExHeader := (body[0] & 0x80) != 0` 即可无歧义同时支持两种线上形态（已在 §3.2.1 合成样本验证）：

| 首字节特征 | 封装规范 | 字段布局与解析规则 |
| --- | --- | --- |
| `(b[0] & 0x80) == 0` 且 `(b[0] & 0x0f) == 7` | 传统 FLV AVC | `frameType = b[0] >> 4`（`1` 关键帧）；`pktType = b[1]`（`0` `avcC` 头、`1` NALU、`2` 结束）；`cts = SI24(b[2:5])`；载荷 `b[5:]` |
| `(b[0] & 0x80) == 0` 且 `(b[0] & 0x0f) == 12` | **国内非标 FLV HEVC**（抖音/B 站 CDN 最常见） | 与传统 AVC 字节偏移**完全一致**：`frameType = b[0] >> 4`；`pktType = b[1]`（`0` `hvcC` 头、`1` NALU、`2` 结束）；`cts = SI24(b[2:5])`；载荷 `b[5:]` |
| `(b[0] & 0x80) != 0` | **Enhanced RTMP / FLV v1/v2** | `frameType = (b[0] >> 4) & 0x07`；`pktType = b[0] & 0x0f`；若 `pktType == 5`（`Metadata`）直接跳过；否则 `fourCC = string(b[1:5])`（支持 `"hvc1"`、`"avc1"`）：<br>• `pktType == 0`（`SequenceStart`）：载荷 `b[5:]` 为 `hvcC` / `avcC`<br>• `pktType == 1`（`CodedFrames`）：`cts = SI24(b[5:8])`，**载荷从 `b[8:]` 开始**<br>• `pktType == 3`（`CodedFramesX`）：**无 3 字节 CTS（`cts = 0`），载荷直接从 `b[5:]` 开始**<br>• `pktType == 2`（`SequenceEnd`）：流正常结束标记 |

#### 4. 断电与崩溃恢复机制对比：先落盘 `.flv.part` vs 实时写 fMP4 `.mp4.part`

| 对比维度 | 备选方案 R1：录制期写原始 `.flv.part` + 周期 `fsync`，停止/恢复时扫描完整 Tag 转 MP4 | **推荐方案 R2：录制期按 GOP（1～2 秒）实时组装 fMP4 `moof+mdat` 追加至 `part-%03d.mp4.part` + `fsync` checkpoint** |
| --- | --- | --- |
| 磁盘峰值空间与总写入量 | 收尾需“读 `.flv.part` → 写临时 fMP4 → `Defragment` 写 `.mp4`”，10 GiB 直播需额外写入两次 10 GiB，峰值磁盘占用达 **20～30 GiB** | 录制期直接写 `part-%03d.mp4.part`（fMP4），收尾与现有 HLS-fMP4 完全一致只调用一次 `finalizeLivePart`（`mp4.Defragment` + `download.InspectMP4FileContext`），磁盘写入量减少一半 |
| 崩溃恢复实现复杂度 | 需新增 `.flv.part` 专用扫描恢复分支、区分 `.flv.part` 与 `.mp4.part` 两套恢复流水线 | **零新增恢复协议**：每次向 `part-%03d.mp4.part` 写完一个完整 `moof+mdat` 后调 `f.Sync()`，更新 `sess.itemMeta.Live.{PendingFile, PendingBytes, PendingDuration}` 并调 `m.lib.SaveRecordingCheckpoint(sess.itemDir, sess.itemMeta)`（[`internal/library/checkpoint.go`](../../internal/library/checkpoint.go)）原子落盘条目 `item.json`；进程崩溃或断电后重启，现有 `(m *Manager) RecoverOrphanParts()`（[`internal/live/recorder.go`](../../internal/live/recorder.go)）遍历 `meta.PendingParts` 执行 `os.Truncate(partPath, meta.Live.PendingBytes)` 切齐到最后一个完整 `moof+mdat` 边界，随即调用 `finalizeLivePart` 产出正式 `.mp4` |
| 异常流尽早暴露 | 录制时只盲存字节，可能录满数小时后收尾才发现参数集损坏无法转 MP4 | 开播首秒即解析 `avcC`/`hvcC`/`ASC` 并生成 `InitSegment`，编码异常立即反馈给界面与状态机 |

**结论**：采用 **方案 R2（实时按 GOP 刷写 `part-%03d.mp4.part` fMP4 分片 + 复用现有 `SaveRecordingCheckpoint` 与 `RecoverOrphanParts` 恢复管线）**；刷盘粒度设为“遇到下一个视频关键帧且距上次刷盘 ≥ 1 秒（或单分片累积达到 2 秒 / 4 MiB 上限，无视频纯音频流按 2 秒固定间隔）”。
