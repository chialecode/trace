# MVP 路线与阶段验收

本文件是实施顺序与阶段门槛正本。需求/AC 正文在[需求](../requirements.md)，每个 FR/NFR 完整交付批次在[映射](requirements-map.json)，实际结果在[状态](status.md)。所有产品阶段目前均未实现、未验收。

## 1. 迭代原则

依据 DEC-004～008，优先抖音、哔哩哔哩视频，先一个平台闭环。M1 拆为 M1a/M1b/M1c：M1a 是首个视频 MVP，M1c 结束且全部 M1 必须项通过后才可声明 M1 完成；跨 M1/M2 或 M1/M3 条目按正文分别验收各阶段子集。直播、完整多账号和自动质量升级有明确后继，不要求一次做完再可用。

每轮由 A 查现场、选择真实用户流程并完成方案 → B 连续实现/自检/修复 → A 集中审查 → 必要人工反馈 → 回写需求/设计/事项 → 下一轮。M0 只消除当前 MVP 的真实风险，不建设完整平台框架或等待未来远程研究。

## 2. 阶段、进入条件与退出证据

| 阶段 | 可交付结果 | 进入条件 | 退出证据 |
| --- | --- | --- | --- |
| M0 最小风险验证 | 模拟视频源经过发现、文件提交、重启恢复和基础界面；验证独立后台与开源基础选择 | 本框架、有效方向；A 先完成当前技术推荐 | 稳定身份/重复提交、文件与数据库中断窗口、双启动/关 GUI、凭证脱敏、隔离恢复证据；选型/未知边界清楚 |
| M1a 单平台视频 MVP | 添加创作者/账号 → 单平台订阅收录 → 来源/正文/视频浏览与中文搜索 → 关闭 GUI 继续 → 导出和恢复 | M0 与该切片相关风险通过；Q-001、必要依赖及站点范围明确 | 单平台真实闭环，支持范围/质量真实呈现；核心提交/恢复/安全门槛通过；可运行包、A 审查与必要 ACT-002/003 |
| M1b 双平台与管理 | 在抖音/哔哩哔哩中补第二个平台；历史回填、多登录账号/能力状态、筛选与资源管理 | M1a 有稳定基线；第二个平台与对应依赖方案可执行 | 双平台来源独立、相同字节共享、编辑历史与认证失败/恢复；分页/预算和本轮需求证据；手动补查及批量管理完整交互留 M2 |
| M1c 本地能力增强 | 直播检测/录制、缺口、质量比较/升级/回收、多路资源与原 M1 剩余项 | 视频闭环稳定；直播/质量样本及后端验证，适用平台另行声明 | 相关直播/质量/回收/资源 AC 实测，所有 M1 完整范围和性能承诺经确认及验证；不把部分 AC 当全场景完成 |
| M2 管理与扩展 | 本地导入/原地索引、身份修正、对比、迁移、插件独立更新及更多来源 | 本地基础可用，按反馈选择单个完整流程 | 对应 M2 需求/AC、兼容/迁移与实际用户收益，至少不同来源检验协议后再稳定主版本 |
| M3 远程 MVP | Linux 无界面、单所有者网页控制、单配置权威、一个存储后端、文件确认/删除同步 | 本地恢复可靠，远程拓扑/凭证/存储方案定稿 | AC-20～22、Linux 部署、鉴权、离线/重放/确认/唯一副本保护实测 |

M0 可逆原型与不受阻 UI 工作可并行推进；未通过存储或生命周期门槛的功能不能向真实档案开放。阶段内按完整用户结果安排反馈循环；每次计划尽量包含可连续完成的实现、自检、修复和交付，不按工作包频繁交接，不以所有远期研究完成作为进入条件。

## 3. M1a 必须包含的最小闭环

| 流程 | 最小范围 | 关键失败与验收依据 |
| --- | --- | --- |
| 创作者与账号 | 新建/编辑创作者、解析并关联首个平台账号；来源身份稳定 | AC-01 中改名/主页变化子集；完整合并/拆分属 M2 |
| 订阅与收录 | 当前新增视频，最小历史范围可声明；正文、来源、视频/必要附件和观察版本持久化 | AC-03/04/13/19；历史覆盖未知必须显示未知 |
| 文件正确性 | 哈希/引用、基本规格、异常识别、已归档原件可恢复 | AC-02/05 的基本提交与引用子集；自动质量替换在 M1c |
| 登录与敏感信息 | 该站点确有需要时实现最小登录/失效/重新授权；任何凭据从首次使用起隔离 | AC-25 必须，AC-08 的失效与告警子集；多账号/自动补全在后续 |
| 浏览与搜索 | 视频与来源、时间语义、基本分页/创作者过滤、中文字面查询、失败重试 | AC-15 正确性子集、AC-16；不提前承诺十万规模性能 |
| 后台与资源 | 关闭 GUI 下载继续、重连、单写服务、完全退出、受限并发/磁盘检查 | AC-09 下载子集、AC-10/12/23 基础负载子集；直播负载在 M1c |
| 退出适配器与恢复 | 停用不删历史；离线读取；核心清单/文件导出；隔离备份恢复；版本不兼容拒写 | AC-11 非录制子集、AC-17、AC-18 核心格式子集 |

每一子集在执行报告逐项注明场景/输入与未覆盖部分，不能写整项 AC 已通过。视频 MVP 可以关闭尚未实现的自动质量替换、物理回收和直播入口，但必须保留相关身份、数据和恢复约束；必要凭证与备份不是后续增强。

## 4. 完整需求覆盖与演进

`requirements-map.json` 对每条 FR/NFR 记录 `firstStage`、`completeStage`、设计锚点、验收编号和范围说明。首次落地可只是子集；完整阶段不得漏掉需求正文任何验收点。跨 M1/M2、M1/M3 的需求保留多个阶段语义，不能因完整阶段更晚而忽略早期子集。

M2 完整验收涵盖 AC-01 的身份重关联、AC-14、AC-18 插件更新、AC-24 等，M3 涵盖远程 AC-20～22。所有阶段共有 NFR 按涉及的功能持续约束；`completeStage` 表示首轮完整测量/证明范围，不是以后可以豁免。

仅确认当前不影响基本流程、不破坏不变量的改善可进入 LOOP，并写后继批次与复验；核心失败仍需本轮解决。性能数值、质量偏好、实际历史范围和视觉稿的进一步确认按总表处理，不在每个工作包打断用户。

## 5. 验收与发布

阶段交付提供实际包/命令、版本、FR/AC→实现→证据映射、A 审查、已知限制、集中人工步骤及结果。B 自检不是 A 审核，A 技术通过不是用户产品验收。

产品验收与发布是不同动作；存在当前必须项缺失时不得声称阶段完成。推送、PR、合并、发布按具体授权执行，不由路线图自动授权。
