# 文档治理与约束管理

生效依据：2026-09-25 用户要求建立指导 AI Agent 与程序员的文档框架。本文约束文档和开发过程；不把设计提案升级为已实现能力。

## 1. 分层与唯一正本

| 类型 | 正本 | 维护职责 |
| --- | --- | --- |
| 入口 | 根 README/AGENTS/CONTRIBUTING/DESIGN/REVIEW、docs 索引 | 导航和全局触发，不复制细节 |
| 治理 | 本文、[文档登记](document-registry.json) | 有效性、状态、负责人和生命周期 |
| 产品 | [需求](../requirements.md)、[产品原则](../product-rules/core-product-principles.md) | 行为与验收定义；原则引用需求 |
| 技术 | [设计](../design.md) | 不变量、数据语义、协议与恢复 |
| 实施/UI 规则 | `docs/dev-rules/`、`docs/design-rules/` | 触发条件、开发约束与验证 |
| 决策 | [有效决定](../decisions/confirmed-decisions.md)、[设计决策台账](../decisions/architecture-decisions.md) | 来源、理由、状态与替代关系 |
| 当前事项 | [open-questions.md](../decisions/open-questions.md) | Q/OSS/ACT/LOOP 唯一当前状态 |
| 交付 | [路线](../delivery/roadmap-and-acceptance.md)、[需求映射](../delivery/requirements-map.json)、唯一迭代计划 | 分批范围与门槛 |
| 事实与研究 | [状态](../delivery/status.md)、`docs/evidence/`、`docs/research/` | 版本、环境、范围与局限 |
| 模板 | `docs/templates/` | 按需使用的最小记录结构 |

默认数值、字段、状态机、需求与验收正文各有唯一维护位置；其他文档引用链接、编号和明确范围摘要。执行报告不另建待决清单。

## 2. 登记、责任与状态

所有仓库自有 Markdown 登记于 `document-registry.json`，包括根入口及未来模块说明。依赖、第三方 vendor、构建输出与临时测试目录不登记。字段为 `path`、`kind`、`status`、`owner`、`scope`、`reviewed`、`basis`；废弃条目增加 `supersededBy`。

| 文档状态 | 含义 |
| --- | --- |
| active | 在 scope 内生效；不表示产品完成 |
| draft | 可评审提案，可做已授权可逆验证，不冒充最终决定 |
| reference | 历史、研究或证据，仅适用对应版本与环境 |
| superseded | 保留替代者链接，不再作为新实现依据 |

局部提案可存在于 active 文档，但须明确标注并关联 Q/OSS；工程数值不因登记而确认。`reviewed` 是最近内容核对日期，不是批准或测试日期。owner 使用角色：产品负责人、技术维护者、设计维护者、质量维护者、文档维护者；未分配专人时由当前维护者协调。

决定使用 `accepted/proposed/superseded`；继承旧设计的 `accepted-design` 专指设计基线，不代表新增用户批准或实测。执行结果使用 `passed/failed/blocked/not-run`；交付过程使用 `planned/in-progress/ready-for-review/rework-required/accepted`。三类状态正交。产品验收 accepted 须有有权验收者、范围与来源，B 自检不具备此含义。

## 3. 规则表达与编号

“必须/不得”为适用范围的约束；“应当”允许有依据的偏离；“建议/候选/初始目标”不是承诺。规则写清触发、动作与验证。M3 能力的要求不成为 M1 全部工作的前置条件。

保留既有 FR、NFR、AC-01～25、INV-01～12、ADR-001～012，不重用或重排；[兼容基线](compatibility-baseline.json)保存原编号和显式锚点用于检查。新 ADR 从 013 延续。有效用户决定用 DEC，待决 Q，开源/上游 OSS，人工/环境 ACT，后续改进 LOOP；审查 F 编号在每份报告内稳定，完整引用含文档路径。

## 4. 冲突与变更

1. 执行环境和当前有效用户指令先于仓库约定；新决定回写正本与来源，已获授权不重复请示。
2. 按职责找正本，不按修改时间、目录深浅或措辞强弱猜优先级。嵌套 AGENTS 只补充子树要求。
3. 代码解释“现在怎样”，需求/契约解释“应当怎样”。明确实现缺陷、过期文档或需求未定，不默默覆盖。
4. 可明确推导的局部修正自主完成；真正涉及产品取舍、授权或不可逆动作的缺失决定进总表，只暂停依赖部分。
5. 例外记录范围、理由、负责人、替代检查与失效条件；永久改变规则更新正本。模板和 draft 标签本身不产生审批节点。

| 改动 | 最小材料与同步 |
| --- | --- |
| 错字、链接、导航 | 直接修正并运行文档检查，无需 ADR |
| 局部实现/修复 | 相关 FR/AC/INV、实际验证、必要正本更新 |
| 新功能/跨模块流程 | 唯一计划或提案，需求→设计→分批/验收→证据 |
| 选型、公共契约、格式、长期架构 | 决策依据、替代比较、兼容/迁移/恢复与调用方文档 |
| UI | 完整状态、设计依据及相应范围的界面验证 |
| 阶段切换 | 必须项、A 审查、人工边界、状态与后继计划 |

## 5. 生命周期与回写

新文档放职责目录，登记并增加至少一个可达入链。移动时修复链接，稳定入口保留短跳转；显式锚点保持兼容。替代保留旧记录和原因。历史失败不能改写为当时通过，修复后追加复验。

需求/公共契约变化、阶段进入退出、依赖关键升级及发现冲突时复核受影响文档。采用前刷新过期研究，不以修改日期替代查询/实测。临时排障经验形成可重复约束后才写工程规则。

文档采用仓库相对链接、合成样本及可移植变量。真实凭据、账号、档案和个人机器路径不进入公开内容。参考工程用于学习治理方法，不继承其权限、许可证、CI 或技术栈。

## 6. 自动检查与语义审查

运行 `python scripts/check_docs.py`，实际覆盖见[质量门禁](../dev-rules/quality-gates.md)。链接存在不证明需求一致、用户已确认、方案适用或测试真实，仍须人工/Agent 核对。

## 7. 项目关键内容的长期保留

依据 DEC-013，影响后续开发、恢复、验收或维护的内容必须落到仓库文档。聊天可解释背景，不能成为唯一依据；也不要求逐条保存无价值命令流水。

| 关键内容 | 唯一维护位置 | 何时同步/保留要求 |
| --- | --- | --- |
| 用户决定、目标与范围 | 有效决定、需求、路线/需求映射 | 新指示改变范围时；记录来源/日期、保留旧 ID 和替代关系 |
| 技术选择与代价 | ADR、研究文档/资料快照 | 引入/替换依赖前；官方来源、日期/版本、许可/维护、取舍、未验证边界和最小实测 |
| 架构、模型、状态/事务、接口/schema、安全边界 | 技术设计及链接的模块/运行契约 | 改行为或公共接口同批更新；类型/迁移代码解释现状，文档解释语义/兼容与失败恢复 |
| 网站范围/质量/认证/历史与限制 | 每站独立能力表 | 接入、接口变动或现场验证后；来源事实、实际支持和未知分开，注明适配器版本/日期 |
| 实际依赖、许可资产、构建/运行/安装/恢复步骤 | 锁文件、B 建立的依赖台账、环境及操作文档 | 首次工程及每次相关变更；真实命令、前提、产物摘要、限制与恢复入口，不把计划命令写成存在 |
| 实施范围、用例与差异 | 本轮唯一计划 | 长批次开始及影响实施的调整时；计划 ID/修订、基点、工作包/验收和继续边界 |
| 故障、修复、验证和实际产物 | 版本化证据及交付/审查报告 | 自检/交接/返工时；保存原失败及复验，不以最后通过覆盖历史；敏感样本只保留合成或安全摘要 |
| 未决/上游/人工/后续循环 | 事项总表 | 发现和解决同批更新；负责人/阻塞动作/关闭条件明确，其余文档引用编号 |
| A/B 当前交接与 prompt | 计划/同轮交付报告，聊天贴可复制文本 | 双方每次结束任务；记录实际基点、报告、问题和验证入口，不能仅靠会话记忆 |

新专题只有确有独立维护职责时才拆文档，登记并从索引/正本可达。已存在正文就补链接和差异，不建竞争副本。当前事实更新当前正本；日期化研究/失败保留为 reference，写明后续替代证据。凭证、真实账户档案、原始敏感响应和本机私有路径不因“保留关键内容”进入 Git。
