# 文档治理与约束管理

生效依据：2026-09-25 用户要求建立指导 AI Agent 与程序员的文档框架。本文约束文档和开发过程；不把设计提案升级为已实现能力。

## 1. 分层与唯一正本

| 类型 | 正本 | 维护职责 |
| --- | --- | --- |
| 入口 | 根 README/AGENTS/CONTRIBUTING/DESIGN/REVIEW、docs 索引 | 导航和全局触发，不复制细节 |
| 治理 | 本文、[文档登记](document-registry.json) | 有效性、状态、负责人和生命周期 |
| 产品 | [需求](../requirements.md)、[产品原则](../product-rules/core-product-principles.md) | 行为与验收定义；原则引用需求 |
| 技术 | [设计](../design.md) | 不变量、数据语义、协议与恢复 |
| 实施/UI 规则 | `docs/dev-rules/`、`docs/design-rules/` | 触发条件、开发约束与验证 |
| 决策 | [有效决定](../decisions/confirmed-decisions.md)、[设计决策台账](../decisions/architecture-decisions.md) | 来源、理由、状态与替代关系 |
| 开发事项 | [open-questions.md](../decisions/open-questions.md) | 开发/上游 Q/OSS 与用户事项导航；LOOP 在交付状态 |
| 用户事项 | [USER-ACTIONS.md](../../USER-ACTIONS.md) | 用户决定、配置、授权、人工检查的唯一当前状态 |
| 交付 | [路线](../delivery/roadmap-and-acceptance.md)、[需求映射](../delivery/requirements-map.json)、唯一迭代计划 | 分批范围与门槛 |
| 事实与研究 | [状态](../delivery/status.md)、`docs/evidence/`、`docs/research/` | 版本、环境、范围与局限 |
| 模板 | `docs/templates/` | 按需使用的最小记录结构 |

默认数值、字段、状态机、需求与验收正文各有唯一维护位置；其他文档引用链接、编号和明确范围摘要。执行报告不另建待决清单。

## 2. 登记、责任与状态

所有仓库自有 Markdown 登记于 `document-registry.json`，包括根入口及未来模块说明。依赖、第三方 vendor、构建输出与临时测试目录不登记。字段为 `path`、`kind`、`status`、`owner`、`scope`、`reviewed`、`basis`；废弃条目增加 `supersededBy`。顶层 `currentPlan` 指向唯一 `kind=execution-plan/status=active` 文档；历史计划标 superseded/reference。

| 文档状态 | 含义 |
| --- | --- |
| active | 在 scope 内生效；不表示产品完成 |
| draft | 可评审提案，可做已授权可逆验证，不冒充最终决定 |
| reference | 历史、研究或证据，仅适用对应版本与环境 |
| superseded | 保留替代者链接，不再作为新实现依据 |

局部提案可存在于 active 文档，但须明确标注并关联 Q/OSS；工程数值不因登记而确认。`reviewed` 是最近内容核对日期，不是批准或测试日期。owner 使用角色：产品负责人、技术维护者、设计维护者、质量维护者、文档维护者；未分配专人时由当前维护者协调。

决定使用 `accepted/proposed/superseded`；继承旧设计的 `accepted-design` 专指设计基线，不代表新增用户批准或实测。执行结果使用 `passed/failed/blocked/not-run`；交付过程使用 `planned/in-progress/ready-for-review/rework-required/accepted`。三类状态正交。产品验收 accepted 须有有权验收者、范围与来源，B 自检不具备此含义。

## 3. 规则表达与编号

“必须/不得”为适用范围的约束；“应当”允许有依据的偏离；“建议/候选/初始目标”不是承诺。规则写清触发、动作与验证。M3 能力的要求不成为 M1 全部工作的前置条件。

保留既有 FR、NFR、AC-01～25、INV-01～12、ADR-001～012，不重用或重排；[兼容基线](compatibility-baseline.json)保存原编号和显式锚点用于检查。新 ADR 从 013 延续。有效用户决定用 DEC，待用户决定 Q，人工检查 H，授权/配置/外部动作 ACT（Q/H/ACT 只在 USER-ACTIONS 维护，编号不带阶段），开源/上游 OSS，Agent 侧后续改进 LOOP，跨模块变更提案 CHG-YYYYMMDD-简短名称；审查 F 编号在每份报告内稳定，完整引用含文档路径。

## 4. 冲突与变更

1. 执行环境和当前有效用户指令先于仓库约定；新决定回写正本与来源，已获授权不重复请示。
2. 按职责找正本，不按修改时间、目录深浅或措辞强弱猜优先级。嵌套 AGENTS 只补充子树要求。
3. 代码解释“现在怎样”，需求/契约解释“应当怎样”。明确实现缺陷、过期文档或需求未定，不默默覆盖。
4. 可明确推导的局部修正自主完成；真正涉及产品取舍、授权或不可逆动作的缺失决定进总表，只暂停依赖部分。
5. 例外记录范围、理由、负责人、替代检查与失效条件；永久改变规则更新正本。模板和 draft 标签本身不产生审批节点。

| 改动 | 最小材料与同步 |
| --- | --- |
| 错字、链接、导航 | 直接修正并运行文档检查，无需 ADR |
| 局部实现/修复 | 相关 FR/AC/INV、实际验证、必要正本更新 |
| 新功能/跨模块流程 | 唯一计划或提案，需求→设计→分批/验收→证据 |
| 选型、公共契约、格式、长期架构 | 决策依据、替代比较、兼容/迁移/恢复与调用方文档 |
| UI | 完整状态、设计依据及相应范围的界面验证 |
| 阶段切换 | 必须项、A 审查、人工边界、状态与后继计划 |

## 5. 生命周期与回写

新文档放职责目录，登记并增加至少一个可达入链。移动时修复链接，稳定入口保留短跳转；显式锚点保持兼容。替代保留旧记录和原因。历史失败不能改写为当时通过，修复后追加复验。

需求/公共契约变化、阶段进入退出、依赖关键升级及发现冲突时复核受影响文档。采用前刷新过期研究，不以修改日期替代查询/实测。临时排障经验形成可重复约束后才写工程规则。

文档采用仓库相对链接、合成样本及可移植变量。真实凭据、账号、档案和个人机器路径不进入公开内容。参考工程用于学习治理方法，不继承其权限、许可证、CI 或技术栈。

## 6. 自动检查与语义审查

运行 `python scripts/check_docs.py`，实际覆盖见[质量门禁](../dev-rules/quality-gates.md)。链接存在不证明需求一致、用户已确认、方案适用或测试真实，仍须人工/Agent 核对。

<a id="project-records"></a>
## 7. 项目关键内容的长期保留

依据 DEC-013，影响后续开发、恢复、验收或维护的内容必须落到仓库文档。聊天可解释背景，不能成为唯一依据；也不要求逐条保存无价值命令流水。

| 关键内容 | 唯一维护位置 | 何时同步/保留要求 |
| --- | --- | --- |
| 用户决定、目标与范围 | 有效决定、需求、路线/需求映射 | 新指示改变范围时；记录来源/日期、保留旧 ID 和替代关系 |
| 技术选择与代价 | ADR、研究文档/资料快照 | 引入/替换依赖前；官方来源、日期/版本、许可/维护、取舍、未验证边界和最小实测 |
| 架构、模型、状态/事务、接口/schema、安全边界 | 技术设计及链接的模块/运行契约 | 改行为或公共接口同批更新；类型/迁移代码解释现状，文档解释语义/兼容与失败恢复 |
| 网站范围/质量/认证/历史与限制 | 每站独立能力表 | 接入、接口变动或现场验证后；来源事实、实际支持和未知分开，注明适配器版本/日期 |
| 实际依赖、许可资产、构建/运行/安装/恢复步骤 | 锁文件、B 建立的依赖台账、环境及操作文档 | 首次工程及每次相关变更；真实命令、前提、产物摘要、限制与恢复入口，不把计划命令写成存在 |
| 实施范围、用例与差异 | 本轮唯一计划 | 长批次开始及影响实施的调整时；计划 ID/修订、基点、工作包/验收和继续边界 |
| 故障、修复、验证和实际产物 | 版本化证据及交付/审查报告 | 自检/交接/返工时；保存原失败及复验，不以最后通过覆盖历史；敏感样本只保留合成或安全摘要 |
| 未决/上游/人工/后续循环 | 开发事项总表；用户动作在 USER-ACTIONS | 发现和解决同批更新；负责人/阻塞动作/关闭条件明确，其余文档引用编号 |
| A/B 当前交接与 prompt | 计划/同轮交付报告，聊天贴可复制文本 | 发生实际A/B交接时；记录实际基点、报告、问题和验证入口，不能仅靠会话记忆 |

新专题只有确有独立维护职责时才拆文档，登记并从索引/正本可达。已存在正文就补链接和差异，不建竞争副本。当前事实更新当前正本；日期化研究/失败保留为 reference，写明后续替代证据。凭证、真实账户档案、原始敏感响应和本机私有路径不因“保留关键内容”进入 Git。

## 8. 本地与公开资料的边界

按[本地参考与文件规则](../dev-rules/local-reference-and-files.md)发现仓库外索引。参考项目名、私有路径、原始截图、源码摘录与参考关系不进入仓库文档/证据/提交信息。正式依赖与法律归属不受此限制。已有公开的官方技术研究保留来源与法律依据，不以新规则抹去既有事实。

新增/改变的用户动作只在 [USER-ACTIONS](../../USER-ACTIONS.md) 维护当前状态，开发总表保留编号与链接；历史证据保持当时结论。决定仍回写有效决定/需求/契约。

新一轮计划使用固定路径 `docs/delivery/stage-plan.md`；阶段整理按下节执行。证据默认写忽略目录，只有脱敏后必要摘要入库。

<a id="stage-cleanup"></a>
## 9. 阶段开始的整理

每个新阶段开始时整理两件事：

1. **无用的文件**，不论是否纳入 Git。逐个按内容决定原样保留、精炼、提炼有用部分后删除，或直接删除（[9.4](#file-cleanup)）。上一阶段已合并的过程文档与产物是其中最主要的一类。
2. **文档里以前阶段的标签**（[9.3](#destaging)）。

是否纳入 Git 不决定去留：`.env.local` 不入库但必须保留；已入库的过程文档，到下一阶段就是要提炼后删除的内容。目的是让工作树和文档只说明两件事：现在已实现什么，接下来准备实现什么。过去的东西留在 Git 历史里。

### 9.1 触发与执行人

1. 一个阶段的 PR 合并进 main 后，下一阶段的 A 计划必须列出整理清单：路径或目录、是否入库、内容判断、处理方式和提炼去向。A 盘点时同时看 `git ls-files` 和 `git status --short --ignored`（不含 `node_modules`、`target`），并记录 `artifacts/`、`dist/` 的大小。
2. B 在下一阶段分支上执行整理，作为该阶段唯一提交的一部分；A 审查时核对。除非用户另有要求，不单开清理分支或 PR。
3. 不入库的文件整理后仍不入库；从中提炼出要入库的内容，先按[第 8 节](#8-本地与公开资料的边界)去掉私人信息和本机路径。B 在报告的“整理记录”里写明不入库文件各类别的数量、大小和处理结果，不写私人材料名称。
4. 删除已入库内容前，用 `git merge-base --is-ancestor <合并提交> origin/main` 确认它已在 main 历史中。当前阶段的过程证据在本阶段 PR 合并前不删，审查和返工还要用。

### 9.2 处理原则

- **Git 历史即归档。** 已合并阶段的文件都留在合并提交里，需要回看时用固定链接 `https://github.com/chialecode/trace/blob/<完整提交>/<路径>`；工作树不保留副本，链接不指向会变化的 main。
- **先提炼、改入链，再删除。** 仍有效的结论、决定、未关闭事项、用户反馈和测量数值，先写入正本，再把入链改指正本或固定链接，最后删除；文档检查必须通过。
- **不按阶段保留总结。** 提炼去向都是不分阶段的正本：[交付状态](../delivery/status.md)（已实现能力、验证状态、限制、遗留编号）、[有效决定](../decisions/confirmed-decisions.md)与 ADR（决定）、[交付路线](../delivery/roadmap-and-acceptance.md)（待实现范围与验收）、[USER-ACTIONS](../../USER-ACTIONS.md)（用户事项）、`docs/evidence/gate/`（最近一次阶段门禁的公开摘要）。
- **状态不升不降。** passed 仍限定被测版本和子集；failed、not-run、blocked 原样写明，不把历史失败写成通过，也不把未测写成已测。

<a id="destaging"></a>
### 9.3 去掉以前阶段的标签

新阶段开始后，文档不再用以前阶段的标签（里程碑编号、计划修订号 r1/r2、返工轮次）描述任何东西。对当前开发来说，一项能力或问题出自哪个阶段并不重要，文档只区分：

- **已实现**：现在的产品里有，附验证状态与证据；
- **待实现**：当前阶段正在做的，或以后要做的。

| 对象 | 做法 |
| --- | --- |
| 需求与映射 | 阶段列改为状态：已实现、本阶段、待实现；映射里按阶段分组的证据只保留当前有效的一份 |
| 交付路线 | 不保留各阶段里程碑小节；写“已实现能力”（链接状态）、“当前阶段”和“待实现” |
| 有效决定与 ADR | 编号保留；描述去掉阶段说法，需要时间时写日期或提交 |
| USER-ACTIONS | 编号不带阶段；适用版本写提交或稳定包生成日期 |
| 交付状态 | 不按阶段或轮次列行；只写已实现能力、当前阶段、后续 LOOP 与推荐下一步 |
| 路径、命令、脚本与目录 | 用不带阶段的名字，例如 `scripts/stage_evidence.py`、`docs/evidence/gate/report.json`、`artifacts/evidence-runs/<跑次>/` |
| 代码注释与测试名 | 同样适用：描述历史的说法删除，或改写成对当前行为的说明；测试按能力命名（例如 `douyin_post_list_keeps_cursor_on_empty_page`），不以 `m1_`、`r3_`、`c01_`、`f009_` 起名 |

例外：当前阶段名称可以出现在当前计划、报告以及状态/路线描述当前阶段的地方；当前计划与报告的整理清单可以写以前阶段的路径；Git 提交信息与 PR 正文不改写；固定归档链接里的路径可以带标签，链接文字与周围说明不可以。

<a id="file-cleanup"></a>
### 9.4 按内容整理文件

范围是整个工作区。逐个看内容，回答两个问题：现在还有没有使用方（代码、脚本、测试、文档入链或用户）；里面有没有仍有效的内容。再选一种处理：

| 处理 | 适用 | 做法 |
| --- | --- | --- |
| 原样保留 | 仍在用，内容都有效 | 不动 |
| 精炼 | 仍需要，但部分过时 | 删去过时部分；名字带阶段标签或返工轮次的改成按能力命名，入链同步 |
| 提炼后删除 | 不再需要，但部分仍有效 | 先把有效部分写进去处，改好入链，再删除 |
| 删除 | 没有使用方，也没有有效内容 | 删除 |

常见内容的默认判断如下，实际处理以核对内容为准，不按目录一刀切：

| 内容 | 入库 | 默认处理 | 提炼去向 |
| --- | --- | --- | --- |
| `.env.local`、`.local/site-secrets/` | 否 | 保留。需要调整的键列进 USER-ACTIONS，用户同意后再改；不读取、不输出与任务无关的值 | — |
| Profile、用户数据、人工检查正在用的隔离样本、用户提供的参考材料与真实站点目标 | 否 | 保留不动。放置位置不安全时在 USER-ACTIONS 建议移动，用户同意前不动 | — |
| 人工检查正在用的稳定包、锁定版本的媒体资产 | 否 | 保留；同名系列里的中间包与旧版本删除 | — |
| 长期正本：入口文档、USER-ACTIONS、需求、设计、规则、决定/ADR、路线、状态、研究、模板 | 是 | 精炼：删去按轮次追加的过程叙述、旧 SHA 流水账和以前阶段的标签，只留当前结论与链接 | — |
| 阶段计划与报告（`docs/delivery/stage-plan.md`、`stage-report.md`） | 是 | 下一阶段 A 改写计划；报告提炼后删除，由 B 为新阶段重建 | 决定 → 有效决定/ADR；验收定义 → 路线/需求；用户事项 → USER-ACTIONS；Agent 侧未完成项 → LOOP 或新计划；结果 → 状态 |
| 轮次证据：`docs/evidence/gate/` 下的多份 JSON、`artifacts/<跑次>/` 下的日志、截图、样本副本、测量原始数据 | 都有 | 入库的只留最近一次阶段门禁摘要；忽略目录里已提炼的跑次删除，仍被状态或 USER-ACTIONS 引用的先抄出数值 | 状态、固定链接 |
| 探针脚本、一次性审查/聚合脚本、按轮次命名的测试文件与测试二进制 | 都有 | 有价值的断言迁入按能力命名的回归测试；仍在用的工具改成按能力命名；其余删除 | 迁移映射写进整理记录 |
| 构建缓存（`target/` 增量目录、`apps/desktop/dist`）、旧安装包、草稿、提交与 PR 草稿 | 否 | 删除（`target/` 可用 `cargo clean` 整体重建） | — |

不得删除：用户数据与 Profile、`.env.local` 与 Cookie 文件、许可证和第三方声明、ADR（被替代的标 superseded）、有效决定、仍被测试使用的合成样本。拿不准的先在 USER-ACTIONS 问，不删。清理前解析绝对路径，确认在明确的生成目录内且不是指向真实资料的 junction/symlink；不用跨目录通配命令或 `git clean -fdx`。

### 9.5 整理记录与审查

当前阶段报告末尾附“整理记录”：删除与精炼的路径（可按目录写）、理由、提炼去向和归档提交；测试、脚本与模块的迁移映射（旧 → 新，或删除理由）；不入库文件各类别的数量、大小和处理结果。测试数量下降必须由映射解释，不能用删除断言换取通过。A 审查抽查被删内容有没有遗失仍需要的结论，并确认文档、公开与产品门禁通过。

### 9.6 预防堆积

- 测试、审计、打包和基准的运行输出默认写到 Git 忽略的 `artifacts/evidence-runs/<跑次>/`；只把审查需要引用的最终结果复制进 `docs/evidence/gate/`。
- 入库证据优先结构化 JSON/Markdown，总量目标不超过 5 MiB，超出时在报告写明理由。媒体样本不复制进证据目录：合成样本放测试夹具目录或由生成脚本重建。
- 一个阶段只维护一份计划和一份报告，路径固定、不带阶段名；返工和复核在原报告内追加。打包输出复用固定目录名加生成日期，同一阶段只保留最新包和人工检查正在用的包。
- 登记表为阶段性文档标注 `retireAfter: <阶段>`；当前阶段晚于该值时文档检查失败，提醒执行整理。阶段顺序按编号比较。

`.env.local` 与凭证文件按用户配置保护：只读任务必需的键，编辑遵循会话具体授权；无权限时在 USER-ACTIONS 列需调整的键和原因，不复制值。明确受保护的旧测试与失败证据，在没有等价迁移证据前保留原状。逐文档同步其他项目的规则时，记录适用条款、目标正本、实际差异和保留理由，不机械复制其他项目的业务契约或工具配置。
