# 网站适配与下载规则

目标平台为微博、小红书、Instagram、X（Twitter）、YouTube、抖音、TikTok、哔哩哔哩八站；抖音与哔哩哔哩已实现，其余六站在本阶段接入。各站的通道、内容类型、登录、网络与验证要求按[唯一计划](../delivery/stage-plan.md)、[多站契约](../design/multi-site-contracts.md)及有效决定确定，资料见[社交站点研究](../research/social-sites-current.md)。具体网站规则在对应适配器开发前单独研究，通用技术的开源优先不预先指定某个站点下载器；外部解析工具只按[多站契约 §10](../design/multi-site-contracts.md#youtube-media)由 Core 调用。

## 独立能力表

每个站点至少记录：稳定账号/内容 ID、主页变化、用户视频列表与分页范围、置顶/乱序/重复、正文与媒体关系、编辑/删除信号、媒体候选规格、音视频合并、签名地址过期、登录和不同访问能力、请求预算、失败分类以及来源证据。直播尚未进入该批次时标明未支持，不伪造空实现。

一个公开视频可下载，不证明能够收录创作者的历史和更新；某下载器声称“支持抖音/哔哩哔哩”，不证明覆盖需要的接口、身份、质量、字幕、合集或登录能力。不得混淆抖音与海外 TikTok 的身份及规则。

## 实现选择

可评估官方开放能力、适用库、专门工具或站点专用实现，具体取舍留在站点方案。通用 HTTP、解析和媒体处理仍复用合适开源基础；平台规则通过规范化契约连接核心。必要的下载工具只是可替换执行部件，不拥有 TRACE 的来源身份、归档目录、成功判断或回收规则。

方案注明可支持/不支持/未知能力、运行版本、验证日期和回退路径。能证明的范围才进入 UI 覆盖声明；限流、网络故障、权限不足不能直接视作内容被删除。

## 验证与交付

1. A 基于目标需求完成站点研究、范围建议与失败用例；决定先做哪个平台时依据证据，不按候选工具的支持列表猜测。
2. B 用脱敏固定样本验证协议，再在授权账号和内容范围做受控真实验证；缺真实配置不阻塞模拟源、核心恢复与 UI。
3. 必测重复分页、增量/历史并行、旧内容编辑、链接过期/断点目标变化、凭证失效、部分资源失败、取消与重启。
4. 报告逐项说明来源、元数据、实际保存规格、覆盖与限制。模拟适配器通过不能替代真实网站验收。
5. 用户取舍与人工配置进 [USER-ACTIONS](../../USER-ACTIONS.md) 的 Q/ACT；站点规则不对、Agent 目前又没有可行思路的情况（[DEC-037](../decisions/confirmed-decisions.md#dec-037)）统一记在 USER-ACTIONS 的[站点规则暂时做不到的情况](../../USER-ACTIONS.md#site-blockers)，编号 S，写现象、已试过的做法、目前的判断和用户可以帮什么忙，规则本身按多站契约标 `partial` 并写明限制；开发/开源 OSS 在[总表](../decisions/open-questions.md)，可延期 LOOP 在[交付状态](../delivery/status.md#followup-loops)，当前 F 在审查报告，各处只链接他处状态。

真实登录检查与内容访问分开。Cookie存在、query接口分配访客ID、HTTP200、`ok: 1` 均不能证明登录；登录判据必须有“不带 Cookie”的真实对照，访客也能得到的回答不算证明；登录成功也不能证明某类列表完整或某分辨率可得。按[本地凭证规则](data-and-security.md#local-site-credentials)先准备必要输入，授权后有界测试；403/412等受限响应记录并停止，不能返回空列表冒充全历史完成或要求用户为代码解析缺口反复换Cookie。

首个平台形成可用闭环后，再接第二个平台验证抽象。不以完成两个站点全部复杂规则作为第一个可用版本的前置条件。

## 当前两站全类型解析

按DEC-022先使用本地索引里相应站点的解析/分页/录制经验，再检索官方接口、社区协议资料和当前实现补齐规则。逐类型记录端点、参数、响应路径、身份、时间、分页、认证/签名、资源关系、错误和证据等级；常量表含端点不证明已接线，支持列表不证明可用。新增规则与缺口见[当前解析研究](../research/site-parsing-current.md)。站点的全类型范围见唯一计划；参考只读，公开内容不保留其关系/私有路径，合法依赖归属必须保留。
