# 开发协作与完成标准

本规则适用于 TRACE 的持续开发。产品开发采用 A/B 分工；任务具体协作范围以有效用户指示为准，单执行者整理文档时如实记为自审，不套用独立 A/B 验收。规则效力、正本归属与变更规模见[文档治理](../governance/documentation-policy.md)。路线以[先基本功能、再反馈迭代](../delivery/roadmap-and-acceptance.md)为准，实际完成情况见[执行状态](../delivery/status.md)。

## 1. 开始与连续执行

开始时确认用户目标、任务边界、相关需求/验收编号、有效决定和当前文件。保护已有修改；复用当前可用工作区。没有 Git、构建或测试工程时如实说明，不把设计中的目录与命令当成已经存在。

已授权范围内的常规实现、可逆验证、修复和文档同步连续完成，不逐文件、工作包或测试轮次询问是否继续。进度更新报告新发现、已解决问题和下一项验证。用户的新指示回写计划与正本，未受影响的工作继续。

遇到缺失信息，先判断它是否改变产品范围、数据语义、费用、授权或不可逆结果。可以隔离时记录假设并先验证；只有无法合理隔离的依赖动作等待用户回答。集中处理非阻塞问题不代表忽略真实阻塞，用户沉默也不是批准。

## 2. Agent A + Agent B

A/B 是开发职责，可由 AI 或程序员承担，与 TRACE 产品内的平台适配器及运行权限无关。A 负责计划与审核，B 负责实现与自检。职责名称不自动授权创建子 Agent 或其他任务，不授予外部发送、发布、合并等权限，也不要求为每个工作包启动新 Agent。

| 环节 | 责任与交付 | 交接条件 |
| --- | --- | --- |
| A 规划 | 核对实际基线和有效决定；明确本轮可用流程、范围、不变量、失败路径、依赖与验证；涉及通用能力时先按[开源规则](open-source-first.md)查证候选，网站下载规则按[站点规则](site-adapters.md)单独研究 | 一份可执行计划，有依据、顺序、完成证据和真实阻塞；区分已有命令与需要建立的命令 |
| B 执行 | 自行核对一次现场；连续实现、自检、修复和同步正本；保留 A 已明确的修复和契约 | 一份交付报告，逐项映射任务、实现位置、实际验证与限制；可自动完成的工作已闭环 |
| A 审查 | 对照同一计划读取实际交付和证据，复核主流程及关键失败；直接修复明确局部问题，集中反馈较大缺口 | 同一报告中的明确审查部分或独立审查记录，标注审查者、基点、结果与必要复验 |
| 用户决定或验收 | 处理集中列明的产品取舍、真实配置与必须人工检查 | 决定回写正本和事项总表；相同范围的已有授权不重复询问 |

每轮默认“一份计划 + 一份交付/审查报告”。已有等价任务材料直接复用，局部修复可在现有记录补充；不为换 Agent、聊天结束或每次小修建立重复计划。聊天只负责指向仓库材料及说明本次动作，不能依赖隐藏聊天记忆。

计划至少列出预期结果、需要保留的不变量、关键失败路径、范围外事项、完成证据、版本基线和未决依赖。技术选型的初步查证由 A 完成，B 补运行适配验证；不能把“优先开源”写成口号却要求 B 从零重做方案调研。

依据 DEC-010/012，后续 A 的一次计划应尽可能覆盖较长、连贯且可验证的完整交付：前置风险验证、实现、集成、自检、修复、打包、文档和集中交接。长计划以一个基本可用流程为边界，不等于一次建设所有远期功能。每个工作包写依赖、结果、失败路径、验证、自主调整项和真正升级条件；能在同批通过技术门槛后继续的后继工作一并写入计划，不把内部检查点变成逐包 A 批准。

B 发现文件与基线不同，先判断变更归属和兼容性；差异本身不等于阻塞。只有会覆盖他人工作或改变任务含义的冲突才提出具体问题。默认同一文件由一个执行者写入；并行工作明确文件归属或隔离目录。

独立审查必须由另一执行者核对实际文件和证据；同一 Agent 更换角色后的检查只能记为自审。分工审查也应写明审查覆盖，不把仅核对文档结构称为已复核产品行为。

## 3. 自检、返工与版本证据

B 按[质量门禁](quality-gates.md)完成最小充分验证，并按[交接模板](../templates/agent-handoff.md)提供“任务/需求 → 实现位置 → 验证证据 → 状态与限制”。状态使用 `passed`、`failed`、`blocked`、`not-run`；不适用项写原因，不能冒充通过。尚缺实现、测试或脚本是开发缺口，不能转交用户人工试错。

A 先核对证据的版本、环境、样本和覆盖范围，复用仍有效的结果。修复过的范围重新验证；没有相关变化或未解决风险时不要求重复全量检查。历史失败保留，新增跑次给新证据入口，不覆写为过去已通过。

较大返工一次性交回当前基点、需保留的局部修复、全部已确认问题编号和定向复验范围。问题沿用审查报告的稳定编号；B 按原编号回复修复位置与实际验证，A 复核后关闭。只描述相对原计划的差异，不重建另一份竞争计划。

交付记录采用当前仓库实际具备的版本方式：无 Git 时记录文件清单、核对时间及必要摘要；有 Git 时记录分支、基线、交付提交和未提交文件归属。提交、推送、创建 PR、合并、发布按任务授权及实际仓库流程执行；不存在远端或自动化时不得声称已备份、已通过 CI 或已发布。

## 4. MVP 与反馈循环

每轮选一个可完整使用、可观察结果的流程，按“计划 → 实现与自检 → 审查 → 必要人工反馈 → 下一轮”推进。优先让基本功能闭环，后续再按真实问题改进质量、速度、覆盖和体验。不能用建立大量框架、未来平台能力或细节打磨替代当前基本功能。

只有不影响本轮基本使用、不破坏数据/来源/权限/恢复约束且不违背当前必须门禁的问题，才可进入后续循环。给出影响、临时可用方式、负责人、进入后续轮次的条件和复测入口；核心失败不能靠改名为“优化”延期。阶段完成与某个原型通过分别判断。

所有待决定、开源问题、人工操作和后续循环集中于[事项总表](../decisions/open-questions.md)。报告引用稳定编号和本轮证据，不另维护一份当前状态。已决定事项同步需求/设计/ADR 并关闭对应待决项；不把已授权动作重新列为待批。

## 5. 完成标准与下一步

| 交付类型 | 最小完成证据 |
| --- | --- |
| 文档框架 | 职责与正本明确、登记及链接有效、状态真实、未决问题集中且有归属 |
| 功能或修复 | 用户可观察结果、主流程与相关失败路径验证、受影响文档同步、当前阻断问题已处理 |
| 数据或公共契约变化 | 兼容说明、旧样本、迁移及失败恢复证据、使用方同步 |
| 适配器或依赖接入 | 开源评估、锁定版本、最小上游样本与 TRACE 集成验证、故障和退出边界 |
| 阶段验收 | 当前阶段必须用例、目标环境与产物、已知限制和必要人工结果；不能由单个命令成功推断 |

每轮结束给出当前角色结果、阶段判断和一个首选下一步。A 与 B 都必须输出给对方使用的完整可复制 prompt，供用户手动转交；包含唯一计划、当前版本、报告、待处理编号和验证范围。仅给链接或“请对方继续”不满足要求。推荐用户检查时给具体步骤与预期。推荐不自动扩大执行授权。

人工必要项具备审阅条件后集中交付。发现仅部分范围受阻时，写清阻塞原因与下一动作并继续无依赖工作；流程文件、模板或候选状态本身不制造额外审批节点。

## 6. A/B 沟通机制与 prompt 合同

默认采用**仓库材料作为上下文、用户复制 prompt 转交、同一批次集中收敛**。职责分工不自动创建另一 Agent、任务或自动消息通道。用户新指示由当前执行者回写有效决定及受影响正本；另一方读取文件即可恢复上下文。关键项目内容按[保留规则](../governance/documentation-policy.md#project-records)落盘。

| 通信类型 | 发起方/时机 | 必须交付与接收方动作 |
| --- | --- | --- |
| PLAN | A 完成长计划和查证 | 计划 ID/修订、基点、范围、工作包/依赖、契约/失败用例、自主权、阻塞替代、验证和报告位置；输出 A→B prompt。B 核对后连续执行，无须例行回复已读 |
| BLOCKER | 任一方发现真实阻塞 | 事项 ID、已尝试处理/证据、只受阻的动作、推荐决定和可继续范围；依赖部分等待，不把普通错误都升级 |
| DELIVERY | B 完成可执行实现/自检修复/文档 | 唯一报告、交付 SHA、包/入口、逐项证据、限制/事项；输出 B→A 审查 prompt，不自称 A 审查或产品验收 |
| REVIEW / REWORK | A 集中核对版本/证据后 | 全部已确认 F、严重度/复现/依据/位置/验收、A 已修内容和新基点；A→B 返工 prompt。B 按原 F 修复复验，不新建竞争计划 |
| REVIEW-PASSED / NEXT | A 技术审查收敛 | 技术/产品/发布分别判断；下一轮已授权则准备完整计划并给 B prompt，否则给保持基点/等待新计划入口，不虚构后续任务 |

计划大改提升同一计划修订，记录原因/依据/受影响工作项；报告引用实际执行修订。小修追加同一报告，不重写历史。交付后 A 按 SHA 读文件，不把聊天“全部通过”当事实。

双方 prompt 至少含以下内容，交接时填真实值，不提交全是占位符的模板：

1. 接收角色和动作（实施/审核/集中返工/等待新计划），明确完成边界。
2. 仓库入口、唯一计划 ID/修订/路径、相关设计与有效决定，不粘贴竞争计划。
3. 分支、基点/交付完整 SHA、报告、未提交修改归属、必须保留的修复。
4. P/C/F 或 Q/OSS/ACT/LOOP 编号、证据/产物、定向验证与未覆盖范围。
5. 连续完成、自检修复、同步正本与保存版本要求，外部动作仍按具体授权。
6. 要求对方完成后再次提供给下一角色的可复制 prompt，使机制闭环。

prompt 随计划/交付报告保存，最终回复同时贴出可用文本，不能让用户从长报告自行拼接。初轮入口见[本轮 B prompt](../delivery/m0-m1a-agent-b-prompt.md)；B→A 与返工通用文本见[模板](../templates/agent-handoff.md)。无返工问题不编造 finding，未有授权下一批明确不扩建。
