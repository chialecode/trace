# 通用技术开源优先

触发：引入或更换前端框架、组件库、数据库访问、异步运行、HTTP/TLS、媒体、搜索、测试、构建、日志等通用能力，以及升级、打补丁或扩大自研范围。各网站下载规则按[站点适配](site-adapters.md)单独处理。

## 1. 职责边界

优先整合活跃且适用的开源方案。TRACE 主要维护创作者/来源身份、观察版本、归档提交、引用保护、任务编排和统一产品体验；不默认自行实现通用 UI 基础组件、媒体格式、数据库驱动或测试引擎。

“开源优先”不是“看到库就采用”。已有 Tauri/Rust/SQLite 基线继续保留；替换它们须有证据和可追溯决定。前端框架尚未选定，应结合真实页面状态与团队维护成本比较，不能把朴素 HTML 或自制组件当成天然更轻量。

## 2. A 先查证，B 补集成

A 制定具体方案前按[评估模板](../templates/open-source-assessment.md)记录：

| 维度 | 最低依据 |
| --- | --- |
| 来源与版本 | 官方仓库、文档、包/发行链接、查询日期、所评估的稳定版本 |
| 维护与治理 | 是否归档/停维、有意义的近期维护、发行方式、与目标相关的 issue/PR 处理样本；不只看 stars 或机器人活动 |
| 适用范围 | Windows/Tauri WebView 或 Rust 目标，离线、中文/输入法、资源预算、数据与取消/停用语义 |
| 许可与分发 | 实际源码、二进制及资产的许可；构建选项、随包通知与发布方式；GitHub SPDX 只是线索 |
| 集成成本 | 官方扩展点、所需桥接、体积、原生依赖、错误传播、升级影响与替代路径 |
| 实证与未知 | 可控样本结果、未测边界、具体 OSS/Q 项，资料判断与运行证据分别记录 |

维护频率按项目成熟度判断，不能用统一“几个月不发版就停维”的阈值。API 限流或无法联网时记录未知，不补造“活跃”结论；继续无依赖工作。仓库 latest release 可能是子包/预览版，锁版本前核对目标包和稳定通道。

A 给出推荐、备选和集成边界后，B 完成最小接入及真实流程验证。通过上游演示、安装成功、编译成功和产品验收是不同事实。已有可靠评估可引用，关键版本/许可/维护变化时重审。

## 3. 集成与最小自研

- 通过正常 API/扩展点接入，避免复制源码或大面积 monkey patch。数据身份与持久化由 TRACE 持有，界面库或媒体引擎不能成为档案唯一解释器。
- 按选型锁定版本与必要完整性信息，记录依赖声明、第三方通知和包内资产。按批升级并跑相关兼容测试，不在用户启动时盲目替换运行依赖。
- 自研通用能力须说明候选不存在、关键契约不满足、维护/许可/平台阻碍或集成成本的实证；只实现必要缺口，记录未来替换边界。
- 不能因一个上游失败样本立刻重写整个引擎。先区分使用方式、适配、版本、上游缺陷和产品需求不匹配。

## 4. 集中处理开源问题

所有选型缺口、许可/打包问题、维护风险、上游缺陷和临时补丁进入[事项总表](../decisions/open-questions.md) OSS 编号。记录锁定版本、最小合成复现、预期/实际、官方 issue/修复、影响、推荐处置、负责人、截止阶段、阻塞范围和复验入口。

处理顺序为定位层次 → 检索官方资料和已有问题 → 最小复现 → 评估升级/适配/替代/最小补丁 → 集成验证 → A 关闭。仅当涉及产品范围、许可证/发布方式或必要外部授权时交用户决定；技术排查留给开发者。

补丁必须有来源、适用版本、测试、负责人和移除条件。准备好可公开的复现与脱敏材料后，只有已有明确授权才向上游发送 issue、评论或 PR。不能把未发送写成已反馈，也不因为等待上游而暂停所有独立工作。

当前[候选池](../research/open-source-candidates.md)是调研入口，不是采购/采用表。后续选择写入[设计决策](../decisions/architecture-decisions.md)，并更新实际依赖、设计与验证。
