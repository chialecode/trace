# TRACE 需求

本页是“用户要什么”的正本。状态只分三种：**已实现**、**本阶段**、**待实现**。决定来源见[有效决定](decisions.md)，协议细节见[哔哩哔哩协议资料](research/bilibili.md)。

全项目是 Go + MyGo 原生界面（DEC-032）。表内“已实现”指代码与自动化证据完成（以 `main` 上的代码与测试为准），不代表产品验收通过（实机人工体验见 [H-001](https://github.com/chialecode/trace/issues/24)、[H-002](https://github.com/chialecode/trace/issues/25)）。

术语：**订阅**是 TRACE 里代表一个被追踪的人的记录，可以关联多个**站点账号**（哔哩哔哩的 UP 主、抖音的作者、微博的博主、X 的用户，可以跨站）；**登录账号**是 TRACE 自己用来登录某个站点的账号，每个站点一个（DEC-026、DEC-043）。界面上用小字“B 站”“抖音”“微博”“X”区分站点（FR-SITE-002）。

## 1. 产品定位

TRACE 是 Windows 桌面应用，以“订阅”（被追踪的人）为入口，用社交网络式的界面浏览并缓存站点内容（DEC-026、DEC-032）。支持哔哩哔哩（DEC-018）、抖音的视频、图文与直播（DEC-043，第 2.8 节）、微博（DEC-065，第 2.11 节；当前仅经合成样本验证，真实站点待 ACT-023）以及 X（DEC-066，第 2.12 节；当前只经合成样本验证，ACT-024 仅完成 2 次前端静态核对并确认 `Bookmarks` 拆包，完整实测待 ACT-025，X 网页前端变动频繁，首次真实使用仍可能需要跟进修复）。以哔哩哔哩为例：登录后粘贴一个链接，就能看到视频详情，或者某位 UP 主的资料、动态和全部投稿；把关心的人建成订阅、关联他的一个或多个账号，随时检查谁有新动态、谁在直播；可以把一条动态（文字、图片、视频及其弹幕字幕）以最高画质和音质缓存到本机（DEC-024），也可以让订阅按规则自动缓存新动态、开播自动录制（DEC-027）；主页像社交网站的信息流一样汇总所有已缓存的内容（DEC-023），媒体库按图片、视频和直播录像浏览。

移动端（DEC-085，第 2.13 节，待实现）是电脑端的遥控器与查看器：Android 手机在局域网上连到正在运行的电脑端 TRACE，查看资源库、已缓存内容与任务状态并做有限的控制；电脑端没在运行时手机不能用，手机本身不登录、不请求任何站点。

原则：

- **必须登录。** 未登录某个站点时不向这个站点发任何解析请求，也没有访客模式（DEC-018）；各站点分别登录、互不影响（DEC-043）。
- **状态真实。** 风控、限流、未登录、网络失败、内容不存在要分别说明，不显示成空列表或“没有更多”；缓存只有文件完整落盘并通过校验后才标为“已缓存”。
- **凭证隔离。** 登录凭证只在后端使用，加密保存，不进日志、历史记录、缓存文件和界面数据；手动添加的凭证只从输入框单向交给后端一次。
- **克制请求。** 只在用户操作或用户明确开启的规则（定时检查更新、自动缓存、开播自动录制、登录续期）下请求，不预取；规则触发的请求有频率上限，只在应用运行且已登录时进行（NFR-NET-002）。API 请求不自动重试，风控和限流一律停下，规则触发的请求还要退避。媒体文件传输中断时在任务内有限次自动续传（FR-CACHE-005），直播断流时在录制内有限次重连（FR-LIVE-002）。
- **不碰用户的文件。** TRACE 只删除自己登记过的文件；保存位置里用户自己放的文件一律保留。
- **开发者优先与边界清晰。** 全项目采用 Go 语言开发（DEC-032），界面层（`internal/ui`）与服务层（`internal/service`）通过清晰的 Go 接口解耦，让改一处站点规则不牵动界面，也为未来提取远程服务器无头录制模式预留干净边界。

### 2.2 缓存

| 编号 | 需求 | 状态 |
| --- | --- | --- |
| FR-CACHE-001 | 手动缓存：动态条目和投稿条目的“⋯”菜单里有“缓存”，视频详情页有“缓存视频”按钮（DEC-038）。缓存一条动态保存它的正文、发布信息、全部原图，以及其中的视频；转发同时保存原动态。视频按 `bvid` 只存一份，动态和投稿共用。转发的动态和它带的图片、视频存在转发者的文件夹里、与他自己的投稿分开；哔哩哔哩合作视频为某位成员缓存时存在这位成员的文件夹里（DEC-056） | 已实现 |
| FR-CACHE-002 | 最高画质与音质（DEC-024）：视频默认缓存这次能拿到的最高清晰度（同档内按编码偏好），音频默认缓存能拿到的最高音质（Hi-Res 无损 > 杜比全景声 > 192K > 132K > 64K）；多 P 默认缓存全部分 P。清单记录每个分 P 实际缓存的清晰度、编码、分辨率、帧率和音质，以及缓存时站点列出的全部档位。设置页可以改成设定上限（以后需要时） | 已实现 |
| FR-CACHE-003 | 缓存任务（DEC-022、DEC-049 ①、DEC-050 ②、DEC-051 ③、DEC-057 ①②、[DEC-076](decisions.md#dec-076) ⑤、[DEC-079](decisions.md#dec-079)、[DEC-081](decisions.md#dec-081)）：图标栏“任务”入口（角标只数排队和进行中的下载任务，不数直播录制、缓存队列等待项、内容冲突、失败任务与录制异常）通过上下文侧栏切换“进行中”“直播”“待处理”和“记录”四组；“进行中”合并“下载任务”与“缓存队列”子视图，前者列出每个下载任务的对象、进度、速度和状态，可以暂停、继续、取消、重试、移除，应用重启后未完成的下载任务恢复为“已暂停”、用户点继续后从断点续传，每个任务有“详情”列出出错分段、节点域名、错误类别与时间（不含签名地址），后者按卡片列出全部缓存队列（含“历史缓存补全 · 微博”队列，顶部在有待补全历史微博且未运行时提供紧凑“发现 N 条历史微博可补全”+“一键补全”操作条），点开看进度与最近缓存的内容（带封面），结束的队列可以移除；“直播”展示正在录制与最近结束的直播并支持在录制行下原地展开异常明细；“待处理”汇总待处理的 V1/V2 内容冲突（FR-CACHE-010）、失败或未完成的下载任务与最近 7 天录制异常；“记录”展示本次运行的导入导出任务；最近结束的录制可以从列表移除，结束场次的录制异常记录可以删除；这些删除都不删已缓存的文件 | 已实现 |
| FR-CACHE-004 | 状态圆点（DEC-024）：动态、投稿、视频详情、主页信息流和媒体库条目上用小圆点表示缓存状态（DEC-039 起媒体库、DEC-046 ⑦ 起主页不显示；主页只列已缓存的内容）：绿 = 已完整缓存且是能拿到的最高档；黄 = 部分缓存、已暂停或有更高档可升级；红 = 失败、文件缺失或清单损坏；缓存中显示进度圆环；未缓存不显示。圆点带图形符号、悬停说明和无障碍名称，不只靠颜色。重启后保持，删除后同步消失 | 已实现 |
